# Finch community-scout 智能交互改造 Plan

日期：2026-09-27  
代码基线：`flingjie/Finch` `main`，`3c2dedee4591a99ddb08d9645bc47b9e9f89d9c4`  
状态：拟实施；基于代码静态检查，未修改业务代码或验证在线社区数据。

## 1. 产品目标

让 Finch 帮用户**围绕具体问题进入并持续参与合适的社区**：发现公开社区，解释其中实际讨论和可参与空间，用户选择后深入阅读，参与后根据真实结果决定继续、观察或离开。

保留此前已选择的「每周深度推荐 3 个社区」作为周报默认上限，而不是每次对话都强制产出三张七字段卡。支持临时提问、指定链接、已有社区回访。更重要的成功信号是用户是否在合适场合形成有价值的持续讨论或贡献；卡片数量和社区总分只是辅助诊断。

边界：公开可访问资料；Finch 只读发现、分析、建议和记录，用户亲自加入、发言、贡献。不借用私有 Discord/Slack 消息，不把他人经验当用户实践。不引入通用 Graph Runtime、向量库、自动调权或另一套总控 Skill。

## 2. 当前实现与症结

| 实际位置 | 当前行为 | 调整点 |
|---|---|---|
| `skills/community-scout/SKILL.md` | 每周 3 张固定行动卡；采集、判断、去重由 Skill 执行 | 增加意图模式、候选分层、按需深入与连续对话；周报保留 3 个默认深推 |
| `references/scoring-rubric.md` | 四维权重 35/25/20/20；近 30 天活动、具体入口、公开来源均是入选硬门槛 | 把「可核验」作为证据条件；「近期入口」作为立即参与条件；未知或暂无入口可进入观察，不伪装为低质量 |
| `references/presentation.md` | 每张卡固定七个问题 | 首页给取舍与一个下一步，详情再展开证据、人物、贡献与成本；用户要求周报时给足交付 |
| `finch community discover` | 生成本地 `profile.yaml` 上下文并读取已有周报；**不进行公开搜索** | 文案改为 `context`/`report` 等真实语义，或保留旧命令并明确说明；Skill 明确执行只读公开搜索 |
| `communities/models.py` | `CommunityProfile` 保存名称、分数、证据、入口、贡献、周次；`CommunityFeedback` 有状态和备注 | 加轻量候选状态及意图/证据时间；区分候选、可参与机会与实际反馈 |
| `communities/service.py` | 保存卡片、记录反馈；反馈不影响后续判断 | 汇总实际反馈供 Skill 读取和解释，谨慎调整本轮推荐理由，不自动改权重 |
| `communities/repository.py` | 候选和反馈追加到 JSONL；同 ID `inspect` 取最后一条；`list` 会返回重复保存的候选 | 提供按稳定 ID 的最新投影与完整历史；同次重复保存幂等；保留旧数据可读 |
| `cli.py` | `feedback` 不校验社区存在；`discover` 写上下文但不会创建周报 | 校验状态动作，区分观察/选择/已发生互动；更新帮助与 JSON 契约 |

现有 `skills/_shared/dialogue-policy.md`、`agent-presentation.md`、`topic-dialogue` 与 `finch dialogue` 已提供任务后延伸与讨论摘要。复用它们，不在 community-scout 中复制一套对话状态机。`People/peer-discovery` 保存真人关系事实；社区领域只保存社区本身、公开入口和用户对社区的反馈。

## 3. 目标体验与决策规则

### 3.1 三种入口

| 用户意图 | 示例 | 首轮交付 |
|---|---|---|
| 本周探索 | “这周有哪些值得参与的社区？” | 最多 3 个不同参与价值的社区，点名首选及原因；合格不足就如实给实际数量 |
| 围绕问题 | “哪里适合讨论 FDE-Gym 的失败回放？” | 优先一个能回应此问题的当前讨论，再给一个不同路径的备选；没有现成讨论就提出观察/贡献路径 |
| 指定社区/回访 | “Temporal Community 最近值得回去吗？” | 读历史选择、实际反馈和新的公开证据；给继续、观察或暂缓的建议，不把旧加入状态等同于活跃交流 |

当前问题、实践引用、历史互动和可投入时间只在有据可查时使用。用户一句话给出的临时意图只影响本次搜索，不静默写入长期兴趣。用户没有给时间预算时不假定其有时间写代码；默认建议轻量、真实的一步。

### 3.2 候选分层而非一次打分淘汰

1. **公开发现**：来源、规范 URL、最近观察时间和可访问范围可记录；来源失败披露覆盖缺口。
2. **可观察候选**：有具体、可核验的实践或讨论证据，但未必有此刻适合参与的帖子；可以推荐阅读，不能杜撰切入点。
3. **当前可参与**：有仍相关的具体话题，且能说明用户可以提问、分享经证实的经验或贡献什么；检查发布时间、状态和讨论是否仍开放，信息不足标未知。
4. **持续参与**：用户确实加入、发言、收到回应、再次互动或贡献；优先读真实未完成讨论及承诺，而非重复给首次加入建议。

“近 30 天活动”保留为周报及时性的默认搜索窗口和诊断信号，不能无条件否决一个高价值但更新较慢的开源社区。无可核验公开证据不能作肯定推荐。成员规模、热度和单个 LLM 总分不能决定优先级。

排序先看当前问题匹配、可带入的本人材料、具体参与入口、互动开放度、交流成本；再考虑实践差异和意外发现。保留四维 `fit_score` 供旧卡读取/诊断，不把分数当作唯一排序与用户面前的结论。前台解释关键取舍，例如“更适合提问”与“更适合贡献复现案例”。若没有真实可贡献素材，允许诚实提出具体观察与提问，不生成“我曾经验证过”的虚假第一人称经历。

### 3.3 连续交互

首轮完成原任务；最多就一个可能改变下一步的分歧追问。用户说“太官方”“英文门槛高”“先看看他们怎么做”，Finch 复用本批候选与来源，只按新要求有界补查。用户选中某一社区后再深读若干讨论和关键 Builder；没有选择不批量生成回复、贡献方案或人物档案。

建议动作限定为：读一条具体讨论、提出一个有依据的问题、准备一段回应、贡献一个确有需要的案例/代码、观察或暂缓。准备草稿必须由用户选中；真实公开互动仍由用户执行。用户转向更广泛的观点探讨时沿用 `topic-dialogue`；涉及真人深入画像或实际关系跟进时交给 `peer-discovery` / `conversation-follow-up`，传来源引用，不复制事实。

## 4. 一次真实使用的示例

> 用户：找一个适合讨论 Agent workflow failure replay 的社区，我有 FDE-Gym 的案例。
>
> Finch：首选 A，因为其最近有一个可读的恢复机制讨论，问题与你的失败回放案例相交；B 更适合贡献评测样例。A 的入口与证据在这里……目前不清楚他们是否已经有同类 replay 工具，我建议先核对这件事。
>
> 用户：先查 A 有没有类似方案，别起草回复。
>
> Finch：读相关公开讨论，说明已有方案、你可能补的缺口和无法确认之处。若没有实质缺口，建议观察或转向 B。
>
> 用户：我已在 A 回复，链接是……
>
> Finch：核对链接和可见内容后记录“已发生互动”；下次回访围绕回应、新问题和承诺，而不是重推“首次加入”。

上例是目标行为，不是已经运行过的社区检索结果。

## 5. 最小数据与接口改动

优先复用 `CommunityProfile`、`CommunityFeedback`、文件 Workspace 与现有 Skill。新增字段均可空、有默认值，旧卡继续可读：

| 字段/记录 | 用途 | 注意 |
|---|---|---|
| `canonical_url` 或 `community_key` | 跨周识别同一个社区 | 优先稳定主页/项目链接；旧 name-hash ID 继续解析，不能仅凭名称把不同社区合并 |
| `intent`、`question`、`practice_refs`、`source_checked_at` | 说明本次匹配对象和资料时效 | 长期兴趣与本次问题分开；引用可空但不可编造 |
| `recommendation_state`：`observe / actionable` | 区分值得观察与当前可参与 | 由证据支持，不等于用户已加入 |
| `entry_point.url/status`（可空） | 指向确切讨论及开放性 | 旧 `discussion/suggested_angle` 兼容读取；未知时不声称可发言 |
| `feedback.reason` 或复用 `note` + `reason_kind` | 理解选择/拒绝原因 | “没时间”是当次约束，不自动变成长期负面偏好 |
| `interaction_ref`（可空） | 用户报告的真实互动链接 | “准备/打算”不能记成 `interacted` |

建议增加的薄 CLI 能力：

```bash
finch community context --json                  # 现有 discover 的上下文部分；如保留 discover 则标明不搜索
finch community list --latest --json            # 同社区最新投影及最新反馈
finch community inspect <id> --json
finch community feedback <id> --result saved --note "先观察恢复机制讨论"
finch community feedback <id> --result interacted --ref <公开链接>
```

接口名称在实现前须核对 Typer 约定。周报生成责任明确放在 Skill：读上下文 → 有界公开搜索 → 保存有证据的卡/报告 → 呈现。若不自动写 `reports/<week>.md`，则 `discover` 不得把候选列表称为已生成周报。对 `joined`、`interacted`、`repeated`、`contributed` 等已发生状态，要求用户明确报告；可验证的公开引用尽量核对，可无公开链接的私下真实事件应允许用户自述并标来源类型，不能假装公开核验。

Repository 对最新投影去重，原始候选与反馈历史保留；重复 `save` 不应令本周展示重复。状态更新不靠字符串大小比较，未加入也可能贡献公开 Issue，实际事实按事件记录，不强制单线性状态机。若 JSONL 无事务并发能力，维持单用户串行写假设并提供稳定重试键，不引入新数据库。

## 6. Skill 与搜索预算

改 `skills/community-scout/SKILL.md` 及三个 reference：

- `scoring-rubric.md` 改为“证据检查 + 情境判断 + 取舍解释”，保留旧分数说明以兼容；为观察/参与分层写清例子。
- `presentation.md` 提供周报、按问题探索、选中深读和回访四种呈现；默认先给一句明确建议、必要来源、一个下一步，详情按需展开。
- `community-card-schema.md` 给观察态、可参与态与旧卡示例；字段可空的语义要明确。
- 对齐 `_shared/dialogue-policy.md`；不规定 4–6 轮，不每轮强行追问。用户说“只看结果”时直接交付。

建议初始工作预算（试运行参数，不是性能承诺）：一次周探索最多 20 个跨源候选，筛到 6 个读近期证据，深入最多 3 个并展示最多 3 个；问题模式优先 1 个、备选 1 个；一次选中深读最多 5 条相关公开讨论，必要时说明为何增加范围。分源失败返回部分结果和缺口，不因一处超时伪造全网结论。对规范 URL 与作品指纹去重，缓存有时间戳；重试计入预算。

GitHub Discussions、Reddit、V2EX、X 与公开论坛按现有只读能力选择；Discord/Slack 只读公开页面。不要为了满足覆盖数抓登录后内容，也不把“社区主页可访问”当成“近期讨论可访问”。

## 7. 分阶段实施与验收

### P0：建立固定样例与基线

- 记录实施时最新 HEAD，核对 `AGENTS.md`、产品契约、所有社区引用和 CLI 返回。
- 准备来源可重放的样例：有价值但更新慢、热闹但无深度、无可切入讨论、已有互动待跟进、同社区多名字、一个平台不可用、用户暂时没时间。
- 保存旧 `CommunityProfile`、反馈与周报样例，确认迁移阅读行为。

验收：准确区分“没有社区”“没有可验证来源”“有社区但当前不宜发言”；有一份可比对的旧版输出。

### P1：先改交互与 Skill（最小可用）

- 更新 Skill 的三个入口、分层判断、选中后深读和自然语言取舍。
- 周报保留最多 3 个深入推荐；按问题不强求 3 个；没有入口可建议观察。
- 修正 `discover` 的说明与 Skill 步骤，让用户清楚何时实际搜索，何时只读本地快照。
- 先以现有卡字段运行 5 次真实任务，记录用户为何选/不选；新字段仍可用 `note` 表达。

验收：用户说“先了解”“不要起草”“不想参与这个”时，后续步骤正确改变；无材料不编亲历；首轮无需填满七项才有有用答案。

### P2：最小状态与反馈闭环

- 扩展 models/repository/service/CLI 的兼容字段、稳定社区标识、最新投影、反馈引用与校验。
- 回访优先使用已发生互动及未完成承诺；报告参与建议与真实事件分开。
- 针对当次“太官方/太泛/时间不够/有深度但暂不参与”等反馈改变下次解释和候选选择；先写可解释规则，不自动训练新权重。
- 可选择在现有 weekly reflection 中增加一段社区参与回看，避免把社区互动重复计为新真人关系。

验收：旧卡可读；重复保存不重复展示；不存在的社区不能默默写反馈；已互动不再收到首次加入建议；“没时间”不导致永久过滤。

### P3：四周真实试运行与调整

- 每周抽查最多 3 个推荐案例，记录资料时效、用户选择、实际参与、收到的有效回应、是否再次出现以及花费时间。
- 复盘误推原因：相关却无入口、跨平台重复、互动开放度误判、用户素材不匹配、社区质量高但参与成本过高。
- 只有反复出现的误判才调整搜索窗口、预算或评分解释；稳定之后再考虑把部分语义规则代码化。

验收：四周结束时能指出哪些推荐真的帮助形成讨论或贡献、哪些仅供阅读，并给出有证据的下一轮调整。未发生的用户反馈和未来互动不得在开发验收中模拟成产品效果。

## 8. 有意义的回归检查

| 场景 | 必须成立 |
|---|---|
| 旧卡缺少新字段 | CLI 仍能 inspect/list；历史 ID 和反馈可查 |
| 同社区本周重复发现 | 最新投影一条；来源历史保留；不会重复计展示 |
| 有实践证据但暂无线程 | 可观察，不声称能立即参与 |
| 讨论已经关闭或无法读取 | 不建议直接发言，标明核验局限 |
| 用户没个人实践材料 | 可基于观察提问，不生成虚构案例 |
| 用户只说“考虑看看” | 最多保存意向，不记录已加入/互动 |
| 用户说“我回复了” | 按其报告记录真实事件及来源；未核验不声称已核验 |
| 候选搜索部分来源失败 | 披露覆盖范围，保留可用结果 |
| 机器 JSON 读取 | 不产生“已展示/已参与”事实 |

运行受影响的社区单测及 CLI 测试，再运行仓库既有 lint、类型和全量测试门禁。语义质量以固定来源样例人工对比；不写只镜像文案的测试。

## 9. 文件范围与完成定义

主要修改：`skills/community-scout/SKILL.md`、三个 references、`src/finch/communities/models.py`、`repository.py`、`service.py`、`src/finch/cli.py`、`tests/unit/test_cli_community.py`、必要的 `README.md` 与 `docs/product-contract.md`。只有真实回访需要时才接入 `learn/reflection.py` 和关联测试。

完成标准：问题模式能找到或诚实说明没有合适讨论；周报能给最多 3 个有公开依据的选择；选中后能继续深读；真实参与可追溯并改变下一次建议；旧数据可读；没有自动发言、自动入群和臆造个人经验。实现时对照当时的最新 HEAD 调整文件与命令，不把本 Plan 中建议接口当成已存在功能。
