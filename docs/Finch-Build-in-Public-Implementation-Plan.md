# Finch Build in Public 实现计划

日期：2026-09-15  
范围：Finch 独立改造；不修改或集成 builderDNA。  
状态：待实施。本计划基于本轮确认的需求，不是当前仓库代码审计；文中的模块名、路径和新增命令均为目标设计，实施前必须映射到实际代码。

## 1. 产品决策与验收目标

Finch 帮用户从个人学习、观察和实践中整理有证据的表达，找到可以提供帮助的 Agent Builder，并延续有价值的对话。

用户希望被记住的标签：善于把新概念变成可用工具的人。这个标签决定 Finch 如何选择和表达素材，不代表 Finch 必须负责概念研究、实验设计或工具开发。

已确认约束：

- 首要目标：建立稳定、持续交流的 Builder 同行连接。
- 受众：Agent 工程师与开源 Builder。
- 内容来源：个人学习、观察与观点，不局限于 GitHub commit。
- 读者价值：可复用的方法与工具；结论有实践、代码或数据支持。
- 连接方式：高质量回复并补充证据。
- 时间预算：每周约 4 小时，目标两条输出加持续互动，不设硬性发布配额。
- AI 职责：发现素材、匹配同行、辅助整理；完整草稿按需生成。
- 用户拥有最终判断与表达；MVP 不自动发帖、不自动私信。

首版工程验收：一个真实素材能够形成可追溯表达或回复建议；用户在平台发布后能够登记或同步记录；收到回应后，Finch 能恢复上下文并给出合理的后续交流建议。

## 2. 与 builderDNA 的硬边界

| 任务 | Finch | builderDNA |
| --- | --- | --- |
| 技术趋势扫描、痛点聚类、机会假设 | 不负责 | 负责 |
| 跨来源机会验证、实验设计、Build/Drop | 不负责 | 负责 |
| 个人实践证据整理 | 负责，用于表达与互动 | 不作为 Finch 的依赖 |
| 理解具体 Builder 的工作与问题 | 负责，用于交流 | 不经营关系 |
| 回复、表达、对话延续、风格 | 负责 | 不负责 |
| 工具反馈 | 记录具体对话和反馈原文 | 独立进行产品机会判断 |

两项目不得共享数据库、状态目录、领域模型、内部代码包、Skill、CLI、输出契约或预留集成接口。Finch 不读取 builderDNA 的 Workspace，不设计专用导入器。普通公共仓库、帖子、用户手动输入可以独立成为 Finch 的来源，不需要识别其是否与另一项目有关。

从上一版建议中撤销：ConceptCard/BuildCard 作为主实体、概念验证状态机、concept-scout、experiment-designer、artifact-packager，以及 Finch 内的构建决策。不要因为这些名字出现在计划里就假定仓库已有对应实现。

边界判定：按“功能负责什么决策”划分，不按来源或是否提到人划分。Finch 可以检查表达所引用证据是否充分，但不能升级为产品机会验证。相关帖子推荐允许探索新问题，但不进行行业级趋势聚类。

## 3. MVP 闭环与降级路径

主路径：输入素材 → 提取事实与个人判断 → 匹配讨论/同行 → 整理回复或公开表达 → 用户发布 → 登记互动 → 跟进与复盘。

两条独立入口：

1. 实践驱动：笔记、commit、日志、已有工具 → 找到可能受益的讨论和 Builder。
2. 对话驱动：帖子、对话、特定 Builder 的项目 → 检索个人相关证据 → 决定是否值得回应。

两条入口独立运行；没有 commit 不阻断发现同行和恢复历史对话。

| 情况 | 行为 |
| --- | --- |
| 有可追溯实践证据 | 整理经验、适用边界、工具用法 |
| 有个人观察但证据不足 | 保存为观察或具体问题，提示缺口；不包装为验证结论 |
| 只有外部资料 | 明确来源，不声称亲自实践 |
| 缺少有效增量 | 返回“暂不回复”及原因，不强行生成 |
| 找不到相关讨论 | 允许独立整理原创提纲，不强制匹配人 |
| 相关来源不可访问 | 标记不可用或未知，不编造内容 |

工具链接不是每条内容的强制字段。真实失败、反例和测试方法也可以有复用价值。

## 4. 最小数据模型

优先复用既有实体并增加必要字段，避免为每个认知步骤新建 Card。首版只需要四类持久化对象，字段名可按现有代码调整。

### 4.1 Material：素材与证据

- id、source_kind、source_ref、captured_at、content_hash。
- source_kind：note / commit / log / artifact / post / conversation。
- facts：事实片段、来源定位、观察时间。
- interpretation：用户判断，与事实分开。
- evidence_status：observed / externally_reported / unverified。
- limitations、visibility、redaction_status。
- artifact_ref 可选，指向既有成果；不创建工具开发任务。

### 4.2 Peer：同行上下文

- id、platform、platform_user_id（若可得）、handle、profile_url。
- focus、current_work、context_refs、last_checked_at。
- 不用显示名作为唯一身份；平台身份未能确认时保留待确认标记，不错误合并。
- 不推断私密信息、人格或商业价值，不设影响力总分。

### 4.3 Conversation：对话与跟进

- id、peer_ids、platform_thread_ref。
- events：外部消息 ID、方向、原文或摘要、source_ref、occurred_at。
- open_questions、follow_up_reason、follow_up_status、dismissed_reason。
- relationship_context 从事件派生，允许用户修正；不强制所有关系走线性等级。
- outgoing、incoming、unknown 必须区分。单方回复不能计为双向连接。

### 4.4 Proposal：表达或互动建议

- id、kind（original / reply / follow_up）、material_refs。
- peer_ref、conversation_ref（原创可以为空）。
- value_added、outline、draft（按需）、claims 与逐条 evidence_refs。
- user_position（仅在确实需要确认立场时使用）。
- status：proposed / ready / dismissed / published。
- source_revision、approval_revision、published_ref、published_at。

只有可核验平台记录或用户明确登记发布后，才能标记 published。ready 不表示发布授权，也不表示已发送。修改正文、事实或立场后，使旧确认失效。

## 5. Skill 与确定性代码分工

保留 Finch 统一入口和独立功能入口。不以 Skill 数量为目标，不同时重写语言、存储和业务流程。

| 认知能力 | 首版实现方式 | 输出 |
| --- | --- | --- |
| practice-evidence | 调整既有 commit/笔记提取能力 | 可追溯事实与判断 |
| peer-discovery | 复用搜索能力，按具体实践/问题检索 | 同行和讨论候选 |
| interaction-copilot | 合并同行理解、回复建议、跟进判断 | 贡献点、提纲或不回复原因 |
| author-insight / draft-generation | 优先沿用既有名称，改为按需调用 | 用户观点整理、内容提纲、可选草稿 |
| weekly-review | 先作为统一入口内流程，不急于独立 Skill | 关系变化、反馈与下一步 |

明确保留 twitter-learning、feynman-practice、sticky-message、voice-profile（若仓库命名不同则映射而非创建重复能力）。

- twitter-learning：学习表达、互动方式，辅助理解讨论语境；不变成机会情报系统。
- feynman-practice：按需检查理解，不能伪造验证，也不是所有发布的强制关卡。
- sticky-message、voice-profile：按需优化表达，不改变事实或不确定性。

Skill 负责语义理解和建议；领域服务负责校验、状态、去重、权限、持久化。外部文本视为数据而非指令；模型不能自行扩展工具权限。

保留确定性状态转换、幂等、原子写入；不引入通用 Graph Runtime。若当前已使用文件 Workspace，就沿用；若尚未完成迁移，单独评估，不能把删除数据库作为本计划的前置条件。

## 6. 检索、排序与成本控制

先低成本过滤，再深度理解少量候选：

1. 以用户当前素材、具体问题和历史对话生成窄查询。
2. 按帖子 ID/规范化 URL 去重，过滤已处理、屏蔽和明确无关内容。
3. 确定性粗排；重点看问题匹配、可贡献证据、历史关联、新鲜度，互动量不是主排序依据。
4. 只让小批量候选进入语义判断，并设置同一作者的展示上限。
5. 每条推荐给出“为什么相关、我能补充什么、证据在哪”；缺少贡献点可不展示。

建议初始配置，不是已测量的性能承诺：每次最多取 30 条新候选，最多深评 5 条，展示最多 3 条互动机会、2 条跟进。每周支持选择一个重点主题，但不限制所有对话必须围绕同一主题。

按 source ID + revision/content_hash 缓存提取结果；按素材修订 + 对话修订 +提示版本缓存建议。设置请求超时、总预算与有界只读重试；达到预算返回已有部分结果。不要一次将全部历史帖子和证据塞入模型。

## 7. 交互与命令

自然语言优先：

- “看看今天有什么我能帮上忙的讨论。”
- “这段记录是否值得分享？先帮我理清事实。”
- “给我这条帖子的回复思路，先别代写。”
- “这条我已经发了，链接是……”
- “看看这周哪些对话值得继续。”

默认展示：对方的具体问题、自己的贡献点、证据链接、两三句提纲、一个下一步。只有用户要求时生成完整草稿。

| 建议 CLI 能力 | 行为 |
| --- | --- |
| finch materials add/show | 输入并查看笔记、链接、证据 |
| finch peers discover/show | 查找并理解相关 Builder |
| finch interactions suggest | 生成回复/跟进建议，允许零结果 |
| finch drafts generate | 从已选素材按需生成草稿 |
| finch interactions record | 登记实际发布和收到的反馈 |
| finch conversations review | 恢复上下文并整理后续机会 |
| finch run daily / weekly | 汇总上述领域能力 |

这些是待映射接口，不是现有可直接执行的命令。保留当前真实入口；不要同时新建 finch daily 与 finch run daily 两套命令。先复用已有子命令，不要求用户记忆 ID 或手动 resume。

首版外部发布由用户完成。历史同步仅在已授权读取来源可用时使用；手动登记始终可用。超时、权限失败与未知发布状态不得被当成成功。

## 8. 持久化与安全

- 单对象写入用同目录临时文件加原子替换；增加修订号防止旧草稿覆盖新内容。
- 先采用单写入者/锁，避免多流程并发追加损坏事件文件。派生索引可重建，关键事实只有一个所有者。
- 来源去重用平台 ID 或规范化 URL；互动事件用外部 event ID；重复同步不得重复计数。
- 对超时重跑、模型输出不合法、进程中断保持可恢复；失败结果显式保存。
- 外部内容不能触发发送、删除、读取额外目录等动作。
- 发布候选必须检查密钥、个人数据和未授权公司/客户信息；敏感或范围不明时阻止 ready，要求用户确认脱敏。
- 不能将向海外服务发送公司资料视为默认许可；按项目允许的模型与数据范围配置执行。
- 不删除用户旧素材、草稿或关系记录。结构迁移必须有备份、预演、计数校验与恢复方式。

## 9. 分阶段实施

### P0：仓库盘点与边界冻结

任务：读 AGENTS.md、README、Skill、CLI、存储与测试；运行既有测试基线；列出现有→目标能力映射；确定真实文件路径；识别用户未提交更改；记录来源授权与模型配置。

交付：迁移清单、当前测试结果、具体改动路径、最小纵向切片方案。

验收：每个新增功能都有现有落点或确切新增理由；无 builderDNA 运行依赖；不声称完成尚未存在的迁移。不在此阶段重写全部架构。

### P1：先用 Skill 跑通纵向闭环

依赖：P0。

任务：用一条真实个人笔记或已有工具、一条真实讨论和现有文件持久化能力，跑通事实提取→贡献点→回复提纲→用户发布登记→跟进。先手动提供讨论链接，不以全自动搜索为前提。

验收：五个用例全部通过：有证据回复；无证据不伪装亲历；没有 commit 仍能输入；无贡献允许不回复；旧对话能恢复。

闸门：根据真实使用修订字段和提示，再代码化稳定部分，不先做全套 CRM。

### P2：固化最小领域服务与记录

依赖：P1。

任务：复用/扩展 Material、Peer、Conversation、Proposal；实现状态校验、修订检查、原子写入、事件去重；补齐独立命令；按需生成草稿。

验收：单功能可独立测试；相同输入重跑不新增重复对象；缺失证据的经验性结论无法进入 ready；未发布草稿不计互动。

### P3：加入检索与持续跟进

依赖：P2。

任务：接入已有授权搜索/读取能力；加入预算、缓存、作者去重和候选粗排；同步或手动登记实际互动；生成基于具体新进展/未解决问题的跟进。

验收：每条推荐有来源与贡献说明；屏蔽/已拒绝项不反复出现；断网返回明确的部分结果；无新进展不机械催促同一人。

### P4：整合 Daily/Weekly 与精简遗留

依赖：P3。

任务：daily 汇总互动机会、跟进与一个可分享素材；weekly 复盘关系和反馈；关闭默认批量草稿与自动 Critic 多轮循环；保留必要确定性事实校验；在测试通过后清理确认无用的旧路径与文档。

验收：默认不发帖、不生成大量草稿、不执行概念验证；从输入到两次有信息量的双向交流有完整记录；旧内容可读或有经过验证的迁移路径。

## 10. 测试矩阵

| 测试 | 必须满足 |
| --- | --- |
| 输入笔记，无 commit | 可正常提取观察和证据状态 |
| 模型编造测试指标 | 无来源 claim 被阻止，并显示原因 |
| 外部文章描述实验 | 保留来源归属，不转换为“我测过” |
| 无可用贡献点 | 输出零建议，不填充空泛回复 |
| 同一帖子重复抓取 | 候选、事件和统计不重复 |
| 同显示名的两个账号 | 不自动合并身份 |
| 单方连续发消息 | 不计为持续双向连接 |
| 草稿标 ready 后再修改 | 旧确认失效 |
| 发布读取超时 | 维持未知/待核验，不标成功 |
| 写入时进程中断 | 旧文件完整，重跑不重复写事实 |
| 两个进程同时更新 | 锁或修订冲突可见，不静默覆盖 |
| 资料含提示注入或密钥 | 不执行来源指令，敏感内容不得进入可发布状态 |
| 问“这个机会值得做吗” | 说明超出 Finch 职责，不调用 builderDNA |
| builderDNA 不存在 | Finch 全部单元及集成测试照常运行 |

建立小型人工标注回归集：至少 20 个去敏样例，覆盖有贡献/无贡献、有证据/无证据、不同账号、重复事件和敏感信息。评估推荐相关性、实际增量、事实支持和声音保真。模型评分只做辅助，不能代替来源校验。

## 11. 每周节奏与效果衡量

四小时应是总预算，实验开发属于用户项目时间；不额外塞进 Finch 经营预算。

| 工作 | 时间 |
| --- | --- |
| 选择素材与整理实践证据 | 40 分钟 |
| 两条输出的提纲、修改和发布 | 70 分钟 |
| 回复和延续同行对话 | 100 分钟 |
| 周复盘 | 30 分钟 |
| 合计 | 240 分钟 |

主要指标：滚动 30 天内，在至少两个独立交流时点有实质双向互动的去重 Builder 数。实质互动指围绕具体问题交换案例、代码、反例或明确反馈；点赞、关注、泛化赞同不计。自动识别需可追溯并允许人工纠正。

辅助指标：首次有效双向对话数、实际方法/工具反馈数、有效建议采纳率、每周用户耗时。覆盖不完整时标注“仅基于已登记/已同步数据”。不按粉丝量评价人，不把关系数设成强制增长配额。

前两周先建立基线，不承诺每月固定新增关系数。第二周检查：是否至少完成真实纵向闭环、用户是否在四小时内完成计划动作、推荐是否确实提供增量。关系建立有外部不确定性，不作为代码交付的保证。

## 12. 完成定义与执行约束

- [ ] Finch 产品描述、Skill、CLI 文档统一为连接与表达，不含机会决策。
- [ ] 独立于 builderDNA，可在完全没有该项目的环境运行。
- [ ] 两种入口都跑通；无 commit 不阻断；无证据不编造。
- [ ] 素材、建议、实际发布和对话可追溯，事实与判断分开。
- [ ] 默认提供提纲，草稿按需生成，最终表达归用户。
- [ ] 预算、超时、缓存、幂等、修订及敏感信息检查有测试。
- [ ] 真实发布后才能统计互动；单方互动不算持续关系。
- [ ] 保留 twitter-learning、feynman-practice、sticky-message 与表达风格能力。
- [ ] 原有用户数据被保留，迁移可预演、验证和恢复。
- [ ] 测试和真实纵向用例通过，使用说明与实际命令一致。

交给编码 Agent 的执行要求：先完成 P0，输出真实文件映射后从 P1 的最小闭环开始实施。禁止默认重写语言、引入通用运行时、删除数据、自动发布或集成 builderDNA。以每个阶段可独立验证为提交边界；安全检查与关键数据一致性先代码化，尚未稳定的认知流程先在 Skill 中验证。
