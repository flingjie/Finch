# Finch 产品契约

Finch 帮助用户从真实使用障碍中发现值得自己解决的问题。问题是默认入口与核心研究对象：一个真实用户问题对应多个候选方案。产品是已有方案和替代方案；人物是问题当事人、验证伙伴和潜在合作者。问题与产品通过证据或人工确认关联。

产品发现、反馈研究与关系能力按问题研究需要调用，不要求先经过产品发现或连接创业者。学习（理解解决方案）、实践（试用与反馈）、表达（形成自己的判断）与连接（与当事人、验证伙伴和潜在合作者的关系）按问题研究展开。内容生产不是目的，也不服从连接。

这不是一个「证据驱动的内容生成工具」，也不是 CRM / 线索库 / PMF 漏斗。

## 核心闭环

```text
发现问题 → 对照已有方案 → 比较与学习 → 选择行动 → 反馈与连接
```

- **发现问题**：从真实使用障碍（issue / 讨论 / 用户反馈）中找出值得自己解决的问题。产品发现与反馈研究按需要调用，用来对照已有方案和替代方案，不是必经入口。
- **理解方案**：产品为谁解决什么问题、原来如何解决、新方案为何可能更有价值、哪些价值有证据、哪些只是假设。
- **比较与学习**：围绕同一用户问题比较不同方案，培养产品判断力，提炼可迁移洞察。
- **选择行动**：收藏观察 / 深入研究 / 试用 / 反馈 / 联系创业者 / 小型合作实验。
- **反馈与连接**：通过真实试用体验、具体反馈、公开讨论建立关系，记录真实互动事实。

当前已落地：问题发现（Problem Inbox）作为默认入口；产品发现、方案分析（Solution Explorer）与 `relationships` 周度简报按问题研究需要调用。Product↔Problem 显式关联层、Problem Radar、Investigate 深调查在后续轮次交付。更深的协作、产品比较与洞察积累亦在后续轮次。问题卡片的 `source_checked`（引用已核对）只表示摘录能回溯到来源，不等于主张被支持，也不等于已复现；复现只能由实验结果更新，属后续轮次。

## 北极星指标

> 每周新增或加深多少个「有上下文、可继续」的创业者关系。

问题推进目标：每周至少推进一个有证据支持的投入或放弃决定。实际验证、判断变化和真实反馈分别记录，不汇总总分；这是运行目标，不承诺每周必有产出。

关系之外，每周分别观察、不合成一个总分的五类进展：

- 修正了什么理解
- 尝试了什么及结果
- 形成了什么自己的判断
- 哪些真实交流值得继续
- 问题推进：哪些问题从初步发现推进到更深理解或真实验证

收藏数、发现数、试用数、反馈数都不是核心成功指标。

## 对象所有权

| 对象 | 归属 | 规则 |
|---|---|---|
| `Product` | 产品领域 | 一个待关注的产品：名称、一句话介绍、创业者、目标用户、解决的问题、核心方案、与既有方式的差异、当前进展、证据、为什么值得关注。按规范化产品身份（如 `github.com/owner/repo`）幂等归一化。**不是线索库条目。** |
| `Problem` | 问题领域 | 真实用户问题：受阻场景、证据、受影响用户、现有 workaround；候选方案引用 `Product`（显式关联层后续轮次落地，当前以文本 workaround / 人工确认记录）。按语义身份幂等归一化。是默认入口与核心研究对象，不合成单一总分。 |
| `Founder` | 连接领域（后续轮） | 构建产品的创业者（轻量身份；第一轮只作为 `Product` 的内嵌字段）。 |
| `Solution` | 智能领域 | 选中一个产品后的 8 点理解：为谁解决什么问题 / 原来如何解决 / 新方案 / 为什么更有价值 / 证据 vs 假设 / 值得学习的设计思路 / 谁在构建 / 下一步判断。证据引用必须是产品证据子集；无证据的主张强制标记为假设。 |
| `Insight` | 智能领域（后续轮） | 可复用的产品洞察（真实问题、有特点的方案、设计取舍、未验证假设、可迁移方法）。 |

**三条铁律：**

1. **证据优先**：发现的产品必须有来源工件；卡片字段只依据证据，证据不足则留空或写「未知」，不编造。
2. **证据 vs 假设**：区分「来源明确说出 / 由材料推导 / 未经验证的假设」三层；未引用证据的主张只能标假设，不得伪装成显式证据。
3. **不自动外发**：`gh` 与 `opencli` 只读；公开回复、引用、私信、原创内容默认需要人工批准。

## 硬边界

- Finch 独立运行，不接入、调用或依赖 builderDNA。
- 不共享数据库、状态文件、Python 包、Skill、CLI 或数据契约。
- 持久化纯文件式（`Workspace.atomic_write`）；无数据库、无 Alembic、无通用 Graph Runtime。
- 保留 `finch` 统一 CLI，继续采用 Skill + 领域服务架构。
- 维持 `gh` / `opencli` 只读；不新增外发能力。

## 职责边界

- **LLM** 只生成候选与语义判断（产品卡片字段、方案分析、诊断、摘要候选）。
- **Python** 负责状态机、幂等、去重、产品聚类、确定性打分、证据子集校验、发布门禁与写入。LLM 输出永远不携带 `total` 分；`score_total` / `score_dimensions` 只在代码里算。
- **发布门禁**：未经批准与验证不视为已发生互动或已发布。

## 非目标

- 不是自动化涨粉工具。
- 不是「从 commit 直接发帖」的流水线。
- 不是 CRM / 销售线索库——`Product` 不是 lead；`Founder` 不是商业机会看板。
- 不建设产品适配评分或工具付费漏斗。
- 不追求覆盖所有平台；一个平台失败不取消其他平台结果。

## 已冻结的旧使命服务

第一轮把旧「学习 / 连接 / 表达」使命的领域服务**冻结**（`hidden=True`，从默认 `finch --help` 面移除），代码与测试保留、数据原样保留，验证新方向后再决定删除。冻结范围：`connect`、`peers`、`people`、`connections`、`conversations`、`ideas`、`drafts`、`review`、`voice`、`profile`、`practice`、`article`、`angles`、`methods`、`community`、`dialogue`、`summaries`、`materials`、`problems`、`attempts`、`grounded`、`knowledge`、`collisions`、`experiments`、`inspirations`、`github reflect`、`learn`、`weekly`、`summarize`、`context`。

保持活跃：`init`、`diagnose`、`twitter`、`sources`、`repos`、`products`、`problem-discovery`、`relationships`。只读 adapter（`sources` / `github` / `twitter` / `reddit` / `webfetch` / `ingest` / `opencli`）与基础设施（`storage` / `codex` / `llm` / `settings`）保留复用。

## 第一轮完成标准

`finch products daily` 每天输出 5–10 个产品候选；`finch products explore <id>` 对一个产品给出 8 点理解；`finch problem-discovery discover` 能从已导入讨论抽出有证据门禁的问题卡片。旧使命命令从默认面隐藏但未删除，数据原样保留。
