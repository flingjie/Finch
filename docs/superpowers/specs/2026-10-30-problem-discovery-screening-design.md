# Finch 问题发现筛选规则收紧 设计

日期：2026-10-30
状态：待实施
目标：把问题发现的筛选规则从"凭直觉挑重点"收紧为"优先真实任务受阻、后果可观察、可技术验证"，补三分离与证据收紧四条，增加主题加权，并把每个重点问题的呈现收成五件（含三个新字段：尚未证实什么 / 下一步最小验证 / 验证后的去向）。

> 本文已核对 `main` HEAD 的 `skills/problem-discovery/`（`SKILL.md`、`references/presentation.md`）与 `src/finch/problem_discovery/`、`prompts/problem-discovery.md`。范围**只改 Skill 文档**，不动 Python 模型 / CLI / 抽取 prompt。

## 1. 背景与问题

当前 `skills/problem-discovery` 的筛选依据模糊：流程只写"挑最多 3 个重点问题"，没写按什么挑；`references/presentation.md` 的每项"五件事"（受阻场景 / 已知事实 / 可能影响 / 关键未知 / 建议动作）没有证据收紧约束，容易把"有人声称已修复"当成"已修复"、把 AI triage 当成"维护者确认"、把"贡献者报告复现"当成"已验证"。

一批正向筛选样本（browser-use #4742、browser-use #5067、LangChain #30667、OpenHands #17546）暴露出三类需要收紧的判断：

1. **问题有价值 ≠ 根因已确认**：同一失效可能有多重解释（图片格式 / 大小 / 工具结果编码 / 历史重放）；报告环境涉及别的仓库时，不能只凭 issue 所在仓库就断定修复位置。
2. **"无人处理"不能只看 assignee**：评论里"声称修复"不等于已合并 / 已发布 / 有效；制造页面崩溃不一定复现原报告的重型 SPA 场景。
3. **评论与自动分析不能升级为事实**：AI agent 补充的 triage / acceptance criteria 不是维护者人工确认；"贡献者报告复现"≠"已验证最新 master 仍复现"；多人讨论 / 多人认领 ≠ 多人独立复现。

本切片只改 `skills/problem-discovery/`，把上述判断落成可复用的筛选规则与呈现结构，不新增自动抓评论 / 核对合并状态的能力。

## 2. 已确认的决策

- **字段归属 = 仅改 Skill 文档**：三个新字段不落库、不改 `Problem` 模型 / `prompts/problem-discovery.md` / `discover.py` / `summary.py` / CLI。由 Skill 每次呈现时现算。
- **诚实边界**：Finch 只读已导入正文，不自动抓 issue 评论或核对合并状态。因此"尚未证实——当前版本状态"与"验证后的去向"多数输出为**"待核实" + "下一步去查 X"**；Finch 负责记录"未证实"并给出最小验证动作，**不负责替用户执行验证**。
- **重构而非叠加**：每项"五件事"重构为五件（后三件即新字段），不叠成八件。"可能影响"并入"尚未证实——影响范围"维度，"关键未知"吸收进"尚未证实什么"，"建议动作"升级为"下一步最小验证"。
- **主题加权 = 软规则**：写成 screening.md 里的一个短"优先观察主题"清单（当前一条），不落配置项、不落评分。当前不引入任何排序分数，与"不写总分"不变式一致。
- **四条证据收紧**：全部落进 screening.md 与 presentation.md 的判断边界，作为每次呈现的硬约束。

## 3. 改动

全部在 `skills/problem-discovery/`。

### 3.1 新增 `references/screening.md`

Skill 挑「≤3 个重点」时的筛选真源。内容：

**正向筛选**：优先发现真实任务中的失效，记录可观察后果；能通过技术验证推进的问题优先。

**三分离**：证据强度 / 个人匹配程度 / 当前可参与方式**分别判断**，不合成一个"综合分"。

**不作为主要排序依据**：`good first issue`、无人认领、近期活跃——可作参考，不当主键。

**证据收紧四条**：

1. 有人声称已修复 ≠ 已合并 / 已发布 / 有效 → 写「有人声称已修复，解决状态未证实；优先验证最新版本」。
2. AI agent 补充的 triage / acceptance criteria ≠ 维护者人工确认；可观察标签（如 `priority:high`）不等于人工确认方案。
3. 贡献者报告在某版本复现 ≠ 已验证 → 自己运行前写「贡献者报告在指定版本复现」。
4. 多人讨论 / 多人认领 ≠ 多人独立复现。

**优先观察主题**（可增补，不落评分）：

- Agent 在异常发生后，能否正确停止、保留状态、并恢复执行。优先纳入该主题的问题，同时保留其他真实使用障碍的探索空间。

### 3.2 改 `references/presentation.md`

**逐项结构**：每个重点问题五件，后三件即新字段。

| # | 字段 | 来源 |
|---|---|---|
| 1 | 受阻场景（谁 / 做什么 / 卡在哪） | 保留 |
| 2 | 已知事实（原文支持的行为/环境/结果，带来源链接） | 保留 |
| 3 | 尚未证实什么（根因 / 影响范围 / 当前版本状态，各自可写"未证实/待核实"） | 新，吸收原"关键未知"与"可能影响" |
| 4 | 下一步最小验证（哪一个实验能减少关键不确定性） | 新，升级原"建议动作" |
| 5 | 验证后的去向（修复 / 补测试 / 协助已有 PR / 继续观察） | 新 |

**判断边界**段收紧为：

- 单仓库公开 issue 覆盖有限；不称"普遍需求""商业机会"。
- 区分历史报告与当前仍存在（未核对写"当前状态待核实"）。
- 呈现侧落实证据收紧四条的具体话术（"有人声称已修复，解决状态未证实"等）。
- 制造页面崩溃 ≠ 复现原报告场景；分别记录。

**尚未支持**段保留"修复状态核对 / 问题组 / 去重"，并补一句：Finch 给出最小验证动作，但**执行验证（跑复现、看合并记录）由用户做**。

**默认返回结构**与"形状"示例同步更新：重点问题逐项改成五件；示例措辞对齐证据收紧（如"是否出现在当前版本、是否属于预期释放行为仍需核对"改为"当前版本状态待核实，下一步先查维护者解释与修复记录再复现最小场景"）。

### 3.3 改 `SKILL.md`

- 流程第 3 步："从卡片里挑最多 3 个重点问题（定性、有解释，不写总分，不生成精确无依据的排名）" → 改为"**按 `references/screening.md`** 挑最多 3 个重点问题（定性、有解释，不写总分，不生成精确无依据的排名）"。
- 逐项呈现要求对齐五件结构。
- "边界"段补两条最常用证据收紧话术：issue 关闭 ≠ 已修复（已有，保留并强化）；"声称修复 / 报告复现 / AI triage"不等同于"已修复 / 已验证 / 维护者确认"。
- "参考"段加 `references/screening.md` 一行。

## 4. 非目标

- 不新增自动抓取 issue 评论 / PR / 合并状态的能力（`gh` / `opencli` 仍只读、只读已导入正文）。
- 不引入排序分数、配置项或主题加权参数。
- 不改 `Problem` 模型、不落库、不改 CLI、不改抽取 prompt。
- 不做问题组合并 / 独立反馈去重（仍属 P2）。
- 不把四条正向样本硬编码进 Skill；它们只作设计依据与回归用示例。

## 5. 测试 / 验证

纯文档改动，无 Python 测试。验证方式：用这批样本（或同类输入）走一遍 `add` → `discover` → `summary`，观察 Skill 输出是否满足：

1. 逐项五件、后三件即新字段，且"当前版本状态"未核对时写"待核实"。
2. 命中证据收紧场景时，措辞是"声称已修复，解决状态未证实"而非"已修复"。
3. 主题问题（异常后停止 / 保留状态 / 恢复执行）得到优先纳入，同时未排除其他真实障碍。
4. 不输出任何总分 / 精确无依据排名 / 内部 ID / CLI 命令。
