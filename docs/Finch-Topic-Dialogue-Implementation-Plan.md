# Finch `topic-dialogue` Skill 实现计划

版本：v1.0  
日期：2026-09-15  
状态：Phase 0–1 已完成（Skill MVP）；Phase 2 待真实话题验证；Phase 3–4 未开始  

## 1. 目标与定位

`topic-dialogue` 是 Finch 中一个按需调用的讨论伙伴。它围绕用户给出的一个话题，通过连续对话帮助用户说清自己的判断、理由、适用边界和证据缺口。

它解决的问题是：Finch 已经能发现同行、准备互动和生成草稿，但用户在观点尚未成形时，缺少一个可以来回讨论、逐步澄清判断的入口。直接生成草稿会过早固定表达，也容易把模型的观点误当成用户的观点。

核心结果不是一篇文章，而是一次经过讨论后更清楚的判断。

### 1.1 MVP 默认定位

- 默认场景：用户有一个模糊想法、问题、帖子或材料，想通过讨论形成判断。
- 默认角色：有实践经验、好奇、愿意提出不同角度的 Builder 同行。
- 默认方式：用户先表达，Skill 沿用户回答推进。
- 默认强度：先理解，再挑战影响结论的关键假设。
- 默认节奏：4–6 轮，一次推进一个问题，约 10–15 分钟。
- 默认资料策略：先讨论；事实争议影响判断时，再建议或调用资料检索。
- 默认结束产物：当前判断、判断变化、证据缺口或下一步小实验。
- 默认集成方式：独立入口；只有用户明确选择，才转为观点候选、草稿或真实互动准备。

### 1.2 非目标

- 不模拟某个真实人物的真实想法。
- 不自动把模拟讨论记为真实互动或关系进展。
- 不要求每次讨论形成内容草稿。
- 不把 AI 提出的论点写成用户已经确认的立场。
- 不在 MVP 中新增通用对话 Runtime、Graph、数据库或复杂状态机。
- 不替代 `feynman-practice`、`sticky-message`、`interaction-preparation` 或 `idea-to-draft`。

## 2. 与现有 Finch 能力的边界

| 能力 | 回答的问题 | 与 `topic-dialogue` 的关系 |
|---|---|---|
| `topic-dialogue` | 我怎么看、为什么、边界在哪里？ | 形成或修正判断 |
| `feynman-practice` | 我是否真正理解并能讲清概念？ | 发现理解缺口时按需调用 |
| `sticky-message` | 核心信息是否清楚、好记？ | 判断稳定后优化表达 |
| `interaction-preparation` | 面对具体帖子，应怎样回应？ | 用户选择与真人交流时接入 |
| `idea-discovery` | 哪些实践或讨论值得形成观点？ | 接收确认后的讨论结果 |
| `idea-to-draft` | 如何把确认的观点写成内容？ | 用户明确要求写作时接入 |

`topic-dialogue` 产生的是练习上下文。只有用户明确确认的判断，才能进入 Finch 的观点和内容链路。模拟对话不得写入 `InteractionRecord`、`ConversationThread` 或关系指标。

## 3. 用户体验

### 3.1 触发方式

以下表达触发 Skill：

- “围绕这个话题跟我聊聊。”
- “我有个想法还没想清楚，陪我讨论一下。”
- “先别帮我写，挑战一下这个判断。”
- “读完这个帖子后，我想和你讨论其中的观点。”
- “从有线上实践经验的 Builder 角度跟我聊。”

单纯要求解释概念时不触发；已有明确观点且直接要求写草稿时，交给现有写作流程。

### 3.2 开场

当话题足够清楚时，直接开始，不先展示配置表。第一轮邀请用户给出当前判断或具体经历：

> 你现在对这件事最直觉的判断是什么？最近有什么经历让你开始这样想？

如果用户已经给出明确判断，先用一句话复述理解，再追问最关键的依据。只有缺少必要材料时才询问补充信息。

### 3.3 每轮规则

每轮输出由两部分组成：

1. 用 1–3 句话回应用户刚才的内容，指出其中具体的判断、经验、矛盾或变化。
2. 只提出一个能推进讨论的问题。

每轮从以下推进动作中选择一个：

| 动作 | 使用条件 | 示例 |
|---|---|---|
| 澄清 | 关键概念或对象含糊 | “你说的流程稳定，具体以什么现象为准？” |
| 追溯经历 | 判断缺少具体来源 | “是哪次返工让你形成这个判断？” |
| 检查因果 | 经验到结论之间存在跳步 | “返工来自过早代码化，还是需求本身一直变化？” |
| 探索边界 | 判断可能只在部分条件成立 | “涉及权限和支付时，这个原则还成立吗？” |
| 提出反例 | 有实质性反例能改变结论 | “如果 Skill 无法稳定复现结果，你会在哪一步提前代码化？” |
| 推演后果 | 需要比较不同选择的代价 | “继续用 Skill 两周，最可能积累什么成本？” |
| 寻找证据 | 结论取决于待核实事实 | “什么结果会让你承认这个判断不成立？” |

不得机械轮换动作，也不得为了显得有深度而强行反驳。

### 3.4 节奏控制

- 第 4–6 轮出现清楚判断、关键分歧或证据缺口时，询问继续深入还是整理当前结果。
- 用户说“总结一下”“先到这里”“形成观点”等，立即结束讨论并整理。
- 用户想换方向时，保留当前判断，切换到新角度。
- 连续两轮没有新增信息时，指出卡点并建议总结、查证或设计小实验。

### 3.5 结束输出

默认返回四项，保持简短并尽量沿用用户原话：

```yaml
current_judgment: 用户现在认可的判断
reasoning:
  - 关键理由或亲身经历
changed_during_dialogue: 讨论中修正、收窄或强化的地方
open_gap:
  type: evidence | boundary | concept | none
  detail: 仍不确定的关键问题
next_step:
  type: continue | verify | experiment | save_idea | draft | prepare_interaction | stop
  detail: 可选下一步
```

如果用户没有形成判断，`current_judgment` 应写成“尚未形成”，并保留真正的分歧或开放问题，不能代替用户补结论。

## 4. Skill 文件设计

新增目录：

```text
skills/topic-dialogue/
├── SKILL.md
└── references/
    ├── dialogue-contract.md
    ├── turn-strategies.md
    └── presentation.md
```

### 4.1 `SKILL.md`

包含：

- 触发条件与不触发条件；
- 默认角色、轮数和挑战强度；
- 开场、逐轮推进、结束判断的主流程；
- 一轮一个问题的硬约束；
- 事实、用户立场和 AI 假设的来源区分；
- 转交其他 Skill 时必须取得用户明确意图的规则。

### 4.2 `dialogue-contract.md`

定义：

- 用户观点、AI 推测、外部事实三种内容的标识规则；
- 什么时候可以说用户已经形成判断；
- 何时触发结束检查；
- 结束输出契约；
- 模拟讨论不得进入真实关系记录的约束。

### 4.3 `turn-strategies.md`

收录七种推进动作、选择条件和正反例。重点防止三类坏体验：连续审问、无依据唱反调、过早总结。

### 4.4 `presentation.md`

定义对话文案：自然回应、少用小标题、一次一个问题、不显示内部状态和评分。结束时才使用结构化小结。

## 5. MVP 运行方式

MVP 由 Skill 在当前 Codex 会话内管理短期上下文，不新增 Python 运行逻辑。会话内部维护以下最小状态：

```yaml
topic: 当前话题
goal: explore | challenge
current_judgment: 用户明确说出的当前判断
confirmed_reasons: 用户提供的理由或经历
candidate_assumptions: 尚未确认的推测
open_gap: 当前最重要的缺口
round: 当前轮次
```

这些字段用于 Skill 推理，不直接持久化。用户明确说“保存这个观点”后，才把结束输出交给 `idea-discovery` 或现有观点入口；用户要求发文后，再交给 `idea-to-draft`。用户提供真实帖子并要准备回复时，转给 `interaction-preparation`。

## 6. 外部资料与真实人物

当讨论涉及会显著改变结论的事实争议时：

1. 先指出争议是什么；
2. 询问或判断是否需要暂停讨论查证；
3. 查证后区分外部证据和用户个人经验；
4. 带着查证结果恢复原问题。

如果用户要求模拟某位真实 Builder，只允许基于用户提供或已检索的公开材料构造“可能提出的角度”。输出需明确这是练习假设，不代表本人，不写入该 Builder 的 `PeerProfile`、互动记录或对话线程。

## 7. 实施阶段

### Phase 0：确定产品契约

**状态：已完成**

任务：

- 在 Finch Skill 清单中加入 `topic-dialogue` 的职责和边界。
- 确认模拟讨论不计入连接北极星指标。
- 确认结束后所有持久化与下游流转均由用户显式触发。

完成标准：README、Skill 描述和本计划对核心目标的说法一致。

### Phase 1：实现 Skill MVP

**状态：已完成**

任务：

- 创建 `skills/topic-dialogue/SKILL.md`。
- 创建三个 reference 文件。
- 实现 explore 默认模式和 challenge 显式模式。
- 实现轮数检查、停滞检查和结束输出。
- 添加与 `feynman-practice`、`sticky-message`、`idea-discovery`、`idea-to-draft`、`interaction-preparation` 的按需路由说明。

完成标准：无需新增 Python 代码，可以在 Codex 中完整跑完一次 4–6 轮讨论。

### Phase 2：用真实话题验证

选择至少 5 个来自用户当前实践的真实话题，建议覆盖：

1. Skill-first 与代码化的边界；
2. Agent 可靠性来自模型还是 Harness；
3. Finch 是否需要关系维护工作台；
4. 通用 Graph Runtime 的真实价值；
5. Build in Public 如何产生有价值的同行连接。

每次结束后只记录以下反馈：

```yaml
topic: 话题
new_articulation: 是否说出了之前没说清楚的内容
judgment_changed: 是否修正或收窄了判断
actionable_gap: 是否得到可验证的问题或小实验
felt_interrogated: 是否像被连续审问
wanted_to_continue: 是否愿意继续使用
note: 一句自由反馈
```

通过标准：5 次中至少 3 次满足 `new_articulation`、`judgment_changed`、`actionable_gap` 中任一项，且 `felt_interrogated` 不超过 1 次。

### Phase 3：补最小持久化和转交

仅在 Phase 2 通过后实施。

任务：

- 为确认后的讨论结果定义轻量 `DialogueOutcome`，不保存完整聊天文本。
- 文件 Workspace 新增 `dialogue-outcomes/<id>.yaml`。
- 保存用户确认的判断、理由、变化、缺口、来源引用和创建时间。
- 增加“保存为观点候选”的显式动作，并把来源标记为 `practice`。
- 下游草稿必须继续经过作者立场确认，不能因为完成讨论而自动确认。

建议模型：

```yaml
id: dialogue_<stable-id>
topic: string
current_judgment: string
reasoning: []
changed_during_dialogue: string
open_gap: {}
source_refs: []
confirmed_by_user: true
created_at: datetime
```

完成标准：重复保存同一结果不会产生多份记录；未确认结果不能进入观点或草稿流程。

### Phase 4：根据证据决定是否代码化更多能力

只有真实使用显示出稳定需求时才考虑：

- 可恢复的跨会话讨论；
- 可配置角色模板；
- 自动关联 PeerProfile 的公开材料；
- 讨论质量的长期复盘；
- CLI 命令，例如 `finch dialogue save/show/list`。

不预先设计角色市场、多 Agent 辩论、自动社交模拟或完整对话编排引擎。

## 8. 验收场景

### 场景 A：模糊想法

输入：“我觉得流程没稳定前应该先做 Skill，跟我聊聊。”

期望：从真实经历开始；每轮只问一个问题；最终形成带适用边界的判断，不直接生成推文。

### 场景 B：明确观点，需要挑战

输入：“Agent 的可靠性主要来自 Harness。请挑战这个判断。”

期望：先确认“主要”指什么，再选择能改变结论的反例；不为反驳而反驳。

### 场景 C：没有形成结论

输入：“我还不知道 Finch 是否需要关系工作台。”

期望：允许以开放问题结束；不替用户选择方案。

### 场景 D：转为内容

输入：“这个判断我认可，保存下来并生成一版草稿。”

期望：明确确认当前判断，先保存为观点候选，再调用草稿流程；保留用户原话和来源边界。

### 场景 E：模拟真人

输入：“模拟某位 Builder 和我讨论。”

期望：基于公开材料给出可能的讨论角度，明确属于练习假设，不更新真实关系记录。

## 9. 风险与控制

| 风险 | 控制方式 |
|---|---|
| 对话变成连续提问 | 每轮必须先回应；一次只问一个问题 |
| AI 抢走作者立场 | 只把用户明确认可的内容写入当前判断 |
| 强行唱反调 | 反例必须可能改变结论，并说明关联点 |
| 讨论过长、没有进展 | 4–6 轮检查；连续两轮无新增则指出卡点 |
| 模拟内容污染真实关系 | `practice` 与 `InteractionRecord`、`ConversationThread` 完全隔离 |
| 过早进入写作 | 用户明确要求后才调用观点或草稿流程 |
| 新增架构过重 | MVP 只实现 Skill；验证通过后才增加 `DialogueOutcome` |

## 10. 推荐实施顺序

1. 先完成 Phase 0–1，建立 Skill 与对话契约。
2. 使用五个真实话题完成 Phase 2，并复盘失败对话。
3. 调整开场、推进动作和结束条件，不先增加角色数量。
4. 达到验证标准后，实现 `DialogueOutcome` 和显式保存。
5. 根据实际复用需求决定是否增加 CLI 与跨会话恢复。

第一版成功的判断标准是：用户在讨论后，说出了原本没有说清楚的判断、修正了一个重要假设，或得到一个值得验证的问题。讨论轮数、文本长度和生成草稿数量不作为成功指标。
