# Finch 跨行业连接与灵感助理：第一性原理优化实现计划

版本：v2 · 2026-09-18  
状态：10题需求已确认；本次优化设计与实施顺序，尚未修改仓库代码。  
权威依据：本轮用户采用的10题推荐选项。本文替代此文件上一版的实施细节，保留已确认的产品选择。仓库事实来自本会话此前读取的文件；执行前重新核对 HEAD，不将本计划中的接口视为已有实现。

## 1. 从最终价值倒推设计

Finch 帮助用户认识不同领域中持续创造、分享一手经验的人，在了解与交流中发现新问题、新视角或方法，并记住值得继续的人与想法。

用户投入的稀缺资源是注意力、理解陌生背景的精力、开展真实交流的意愿。增加人物、平台、评分和卡片数量，只有在改善这三件事时才有意义。

三个基本条件决定设计：

1. **接触差异**：看见自己通常不会接触到的实践与人。行业只是寻找差异的线索；行业标签不同不保证认知不同。
2. **理解与参与**：能读懂对方具体做了什么，知道怎样继续了解或交流。跨行业距离太远、背景解释不足，会增加负担。
3. **保留连续性**：记住用户为什么感兴趣、真实交流到了哪里、有什么认识值得重看。无需每次重建上下文。

灵感无法由系统保证。系统能提供可信的差异、合适的入口和可回访的记忆。是否有启发由用户判断；是否采取行动由用户决定。

### 1.1 必须验证的产品假设

| 假设 | 应观察的证据 | 假设不成立时的调整 |
|---|---|---|
| 陌生实践会带来有价值的新视角 | 用户主动选择了解，并能说出吸引自己的具体细节 | 先改样本与解释，不增加平台或算法 |
| 少量背景解释能降低理解成本 | 用户在10–15分钟内完成一次有意义的选择 | 缩短卡片、减少术语、选更可理解的对象 |
| 围绕具体作品更容易展开交流 | 用户能提出真实问题或补充，而非泛泛赞美 | 改善交流切入点，允许先阅读或试用 |
| 轻量记录能支持后续联系和思考 | 用户再次使用已有对话或笔记 | 改善回看时机，不扩大保存量 |

这些是待验证假设，不是研究结论。四周验证提供个人使用证据，不作因果或统计显著性声明。

### 1.2 相比 v1 的优化

| v1 的负担 | v2 处理 | 原因 |
|---|---|---|
| 先完成推荐扩展，再建设灵感记录 | 首个可用版本同时包含发现、选择、保存、回看 | 尽早验证完整价值 |
| 新增多维评分再计算总分 | 基础证据筛选＋简单组合规则；保留必要的现有评分兼容 | 尚无足够反馈校准“视角增量”等数字 |
| 三种探索模式可能演变为三套服务 | 三种输入意图，共用证据与人物服务 | 工作对象相同，只有召回范围不同 |
| Inspiration proposed/confirmed 状态与 confirm 命令 | 系统建议留在快照；用户明确保存后才创建笔记 | 不增加灵感审批队列 |
| 先设计大量结构化字段 | 少量必填字段，解释与反思允许自由文本 | 避免为满足 schema 编造理解变化 |
| 所有主题轮换、画像和重提都一起自动化 | 显式主题＋展示历史；先在用户打开和周回顾时重提 | 控制复杂度与打扰 |
| 日常3人限额混同安全边界 | 建议每天深入1人、最多3人；运行成本另设硬预算 | 用户偏好和系统资源约束需分开 |

## 2. 已确认需求：不因简化而缩减

| 10题决策 | 最终约定 |
|---|---|
| 结果 | 持续关系与新视角优先；小尝试、共同实践为延伸；表达为可选出口 |
| 入口 | 默认自由发现和指定人物/作品/链接；问题探索按需；无问题也能使用 |
| 对象 | 持续创作者、一手经验与失败分享者、跨领域实践者 |
| 范围 | 行业开放，主题轮换；不固定 AI/Agent 或近中远配额 |
| 意外发现 | 少量保留未知用途的可信发现，解释有趣之处与未知项 |
| 下一步 | 阅读、澄清、交流、先实践按情境选择；可以观察或跳过 |
| 灵感 | 用户确认有启发即可保存；无需实验、迁移假设或发文计划 |
| 分析深度 | 推荐理由、机制比较、差异和适用边界；不接管战略或商业判断 |
| 节奏 | 默认每日10–15分钟；首页3个重点；保留每日50人分层浏览；忙时周看 |
| 首版 | 发现＋交流准备＋轻量记忆；不建设完整实验管理与成果发布系统 |

五个平台继续在接入范围内：Twitter/X、GitHub、V2EX、公众号、小红书。具体运行可用性由连接器实际状态决定；不要求全部在线才能完成一次探索。

## 3. 最小产品闭环：两条自然路径，共用同一记忆

路径一：发现人物或作品 → 了解／澄清 → 保存一个启发 → 按需回看。

路径二：发现人物或作品 → 准备交流 → 用户实际互动 → 记录真实对话 → 有新事实时继续。

两条路径可以交汇，但阅读不强制转社交，社交不强制产生灵感，灵感不强制转实验。用户直接输入自己想记的启发，也不必重新走发现流程。

### 3.1 每次打开的体验

- 从同一推荐快照显示至多3个重点，优先不同实践背景；通常0–1个意外发现，合格不足则少显示。
- 每张卡只回答：此人做过什么、有什么具体细节值得了解、证据在哪里、可以怎样继续。
- 有真实回复或待兑现承诺时显示相应事项；不额外强制塞入“每天一个灵感”等内容配额。
- 展开后可看原有50人分层浏览结果；不足50人明确显示缺口。
- 原有5重点/15摘要/30浏览如仍适用可保留；首页3人是独立展示投影，不再产生第二个人物池。
- 明确展示快照时间与来源状态。纯读不触发抓取；首次没有快照时提示一次明确刷新动作。

卡片建议约100–180中文字，作为可用性起点而非硬指标。先把原始实践讲清楚，再提出可选关联。默认一个建议动作，其余动作按需呈现。

假设示例：某位策展人公开复盘如何安排观众理解一件作品的顺序。卡片先呈现其实际尝试，再说明“这个安排方式可能值得了解”。不必强行映射到 Agent 产品；用户选择比较后，再讨论相似机制、差异和未知条件。

### 3.2 自由发现的冷启动

没有历史时，复用用户明确兴趣和一个可编辑的轮换主题列表。主题是查询起点而非封闭行业目录。初期用少量带原始作品链接的实践者种子启动；GitHub 不是所有人物的必要证据来源。

来源不足时允许用户导入人物或作品链接。没有回复记录不等于不愿交流；没有公开仓库不等于没有实践。系统未知的字段保持未知。

### 3.3 三种输入的最小处理

| 输入 | 读取范围 | 产出 |
|---|---|---|
| 自由发现 | 显式主题＋近期展示历史，按预算读取来源 | 一组可理解的人物发现 |
| 人物/作品/链接 | 优先读取指定对象及必要上下文，不先全平台搜索 | 对该对象的了解与下一步 |
| 具体问题 | 围绕问题召回不同背景的实践 | 带差异和适用限制的相关发现 |

自由模式不因缺少“当前问题”被扣分。用户指定对象的结果不必伪装成系统全局排名。

## 4. 推荐系统：把不确定判断留给解释

### 4.1 基础门槛

推荐所依赖的“做过什么”必须能指向作品、一手实践或具体过程记录。仅简介和转发可进入待了解池，但不能冒充实践充分的重点人物。过期信息标时间，不要求所有好作品都是最近发布。

身份归一化沿用既有实现。跨平台同名不能自动合并；无法确定时保留独立档案。外部页面和帖子按数据处理，不执行其中要求改变指令、外发消息或暴露本地信息的内容。

### 4.2 简单选择策略

1. 过滤显式排除主题、失效引用、重复内容及没有支撑的主张。
2. 复用现有排序，必要时调整写死的技术中心偏好；暂不新增“创新总分”。
3. 有界语义处理：给出具体推荐理由与未知项，检查候选是否实质重复。
4. 从候选中顺序选取不同实践背景或不同做法，应用展示冷却；同分使用稳定顺序，保证结果可解释。
5. 有可信且可理解的意外发现时保留一个位置；无合格结果不凑数。

领域标签只是多样性辅助。优先解释“与近期看到的做法有何不同”，不声称能从标签计算客观的认知距离。“新颖”只是对当前已知兴趣和展示历史的估计，用户反馈可纠正。

如已有 LLM 维度与确定性总分，保留兼容直到相关调用完成调整；不新增新分数、不由 LLM 输出权威总分。只有选择规则反复出现可复现错误、且人工例子显示某因素稳定影响结果时，才考虑增加相应排序特征。

### 4.3 成本预算

- 每日50人为浏览目标，沿用一个配置来源；不是50份深度报告，也不承诺全部是当天新发现。
- 只对固定数量候选做语义判断；未做深度判断的浏览卡标注其信息层级。
- 用户选中后才进行详细比较与回复准备。
- 来源调用次数、语义候选数、深度准备次数、总超时使用既有预算；实施时核对配置位置和合理默认值。
- 所有重试计入预算；预算耗尽返回可解释的部分结果。
- 证据未变时复用缓存；用户偏好和比较上下文改变时，相关判断缓存失效。
- 浏览不额外生成卡片。独立 I/O 的有界并行沿用项目规则，不改变有副作用步骤的执行顺序。

不要将 home_limit、browse_limit、daily_people_limit 重复配置。首页3、浏览50、建议每日深入1至3人分别是展示、发现和投入偏好；基础设施硬上限单独管理。

## 5. 架构与数据：先复用，最小新增

采用现有 Skill + Python 领域服务 + 文件 Workspace。模型理解和建议，代码维护事实、引用、预算、状态与幂等；不新增通用流程引擎。

| 现有部分 | 修改方式 |
|---|---|
| sources、OpenCLI/gh、CreatorEvidence | 复用读取、证据与来源状态；补非技术主题种子 |
| Person、PeerProfile | 复用；有来源时记录实践背景，不增加完整行业知识图谱 |
| Opportunity、DiscoverySnapshot | 承载推荐原因、展示历史和可选比较；不新增 CollisionCard 实体 |
| peers/recommendations.py | 复用50人组合，增加首页投影与必要的去重/背景差异选择 |
| InteractionProposal/Record、ConversationThread、Commitment | 保留真实关系主线，不将阅读行为写成互动 |
| collisions、experiments | 盘点并复用已有比较能力；不据命令存在就扩大产品范围 |
| AuthorIdea、Draft、VoiceProfile | 按需使用，保留原来的作者立场规则 |
| learn/weekly、storage、CLI | 扩展原有记忆投影与反馈 |

### 5.1 推荐记录只补实际用到的字段

优先复用既有字段；不足时加：具体推荐理由、来源引用、可选不确定性、建议动作、可选比较文本。相似机制和差异可先放在同一个结构化文本段中；未被检索或验证使用的内容不强拆字段。

来源记录至少保留 URL/来源 ID、读取时间及支持推荐理由的必要片段；引用原有 artifact 即可，不复制整篇内容。快照引用它们，原文不可用时能说明依据与局限。

### 5.2 灵感记录是用户选择保存的笔记

AI 生成的“可能有启发”留在推荐或讨论上下文中，不自动建立长期灵感对象。用户说“记下这个启发”时立即保存，不再追问确认。

保存最小结构：

```yaml
id: inspiration_example
text: "用户想保留的启发；可保留用户原话"
source_refs: []
origin: observation  # observation/conversation/practice/simulation/user_input
person_ids: []
conversation_id: null
created_at: "..."
updated_at: "..."
archived_at: null
```

source_refs 可空，例如用户自发想法；来源空时不能宣称由某个发现或真实对话产生。origin 描述事实来源，不描述证据强弱。保存动作来源记录在既有审计信息中；不得通过设置 origin=conversation 伪造真人互动。

用户反思、迁移假设、下一步和结果作为可选追加笔记，不设必填，不增加实验状态机。保存内容可能由模型整理，应保留可追溯的用户保存意图，并支持修改或归档。

如果已有独立于 ConversationThread 的笔记对象可满足需求，优先扩展；否则新增一个 Inspiration 类型与最薄仓储。无真实对话的灵感不得为了复用而挂入虚假线程。只有存储与检索边界确实需要时才创建 inspirations/ 目录。

### 5.3 幂等与旧数据

- 同一次请求重试使用稳定幂等键；重复执行不产生多份灵感。
- 内容相似只能提示重复，不能自动合并用户不同时间的理解。
- 用户明确“再补充一点”时追加，不能用机器重新生成覆盖原话。
- 旧人物、线程、快照新增字段可空；不批量用 LLM 伪补历史。
- 无用户保存意图证据的历史系统候选保留候选属性，不迁移成用户灵感。
- 试跑 Markdown 笔记导入复用源文件 ID 或稳定键，保留时间和引用；重复导入无副作用。
- 原子写、并发版本检查沿用 Workspace 能力，不另造版本系统。

## 6. 记忆何时重新出现

首版采用明确关联，避免不断推送“你可能感兴趣”：

| 情况 | 行为 |
|---|---|
| 打开同一人物 | 展示相关真实对话及用户保存笔记 |
| 用户请求回看某个主题 | 通过现有文本检索/标签检索笔记，显示来源 |
| 有真实回复、新证据或承诺到期 | 生成一条可去重的继续事项 |
| 周回顾 | 少量展示本周保存与用户手动选定要重看的内容 |
| 只有时间过去，没有新事实 | 默认不建议联系；已有用户主动开启的周期回顾可继续 |

同一触发事件和目标使用稳定键；用户略过同一提示后不每次打开重复强调。跨笔记语义联想先由用户按需请求；自动语义重提、向量库、后台监测暂缓。

## 7. Skill 与 CLI：减少入口负担

保留现有 Skill 名称：peer-discovery 处理不同输入，interaction-preparation 处理选中后的理解与交流，conversation-follow-up 处理真实跟进，weekly-reflection 处理复盘。topic-dialogue 用于澄清与比较；idea-discovery 仅在用户希望形成观点时调用。

灵感保存通过现有 Skill 调用领域命令完成，暂不新增总控 Skill 或灵感审批 Skill。twitter-learning 如存在必须保留；实施前核对目录。

Codex 默认展示自然语言结果和下一步。CLI 保持 finch 统一入口；新增命令仅覆盖无法用现有命令表达的持久化操作。

拟议接口（待核对仓库后映射，不声称已经存在）：

```bash
uv run finch connect daily
uv run finch connect daily --refresh
uv run finch connect daily --view browse
uv run finch connect daily --question "其他行业如何处理责任交接？" --refresh
uv run finch connect prepare --opportunity <id>
uv run finch inspirations save --source <ref> --text "我想保留的启发"
uv run finch inspirations list
uv run finch inspirations show <id>
uv run finch inspirations note <id> --text "补充或后续结果"
uv run finch inspirations archive <id>
uv run finch weekly
```

save 表示用户已明确要求保存；系统自由生成的候选不得调用。用户笔记无外部来源时允许省略 --source。修改正文应复用已有编辑路径或为 save 增加明确更新语义，避免创造另一套命令族。

指定人物/作品复用 connect with/person 或既有来源导入命令，按实际签名实施。相同语义不增加 explore、connections、people 三套新别名。保留原命令和 JSON 消费者；首页是投影，原50人快照继续可取。若机器契约必须变化，显式版本化。

## 8. 分阶段交付：每步验证完整价值

### P0：盘点与验收样例

完成条件：最小修改清单与可重复验收样例齐备。仅盘点代码，不将未执行的在线采集记为通过。

### P1：一条可用闭环，优先级最高

- [ ] 选中人物后支持阅读、澄清或交流准备；不提前给全部人物生成回复。
- [ ] 用现有笔记设施或薄实现保存用户启发，能在查看该人物或周回顾时看到。
- [ ] 在5次真实使用中覆盖三种入口；直接观察用户选择和表达，不要求每次填评分。

验收：无 question 也可发现；用户可只阅读并保存；能再次找到已保存内容；真实互动与阅读记录不混淆。5次只是可用性起点，不能证明长期收益。若多数结果仍空泛，留在本阶段修样本与提示，不先扩大推荐系统。

### P2：只固化试跑稳定的部分

任务：
- [ ] 将P1实际使用的字段与笔记规则落入模型、仓储和 CLI；导入试跑记录。
- [ ] 增加加法式旧文件兼容、幂等键、原子写与引用验证。
- [ ] 接入显式主题轮换、重复展示冷却与简单组合规则；不实现新综合评分。
- [ ] 校验纯读与刷新分离；建立可检查的来源、语义及深度调用预算。
- [ ] 记录实际延迟、调用量与部分失败结果；基于测量确定预算默认值。

验收：重复运行不产生副作用；扩大候选池不突破预算；语义判断失败时保留可信基础结果；首页和浏览层使用同一快照。

### P3：关系延续与反馈回用

任务：
- [ ] 复用事件跟进，关联同一人物、线程和用户笔记。
- [ ] 用稳定事件键去重继续事项，略过不等于拉黑。
- [ ] 增加少量可选反馈：想继续、已经熟悉、关联牵强、证据不足、今天没时间。
- [ ] 用户明确要求排除主题才写长期配置；其他反馈先用于当次/近期选择。
- [ ] 更新 weekly，将真实关系、保存的新视角、可选尝试分开呈现。

验收：新事实能接续已有上下文；无新事实不制造寒暄任务；模拟讨论不进入关系统计。

### P4：四周产品验证与扩展决策

任务：
- [ ] 在相近阅读时间内，对照少量“只给人物＋来源”和“附具体发现理由”的样例，询问哪种更有帮助。
- [ ] 每周查看最多3个真实案例：选了什么、为什么继续/停止、记住什么、是否回访。
- [ ] 检查曝光偏差：是否只有好抓的平台、英文作者、公开仓库作者进入重点。
- [ ] 按具体失败决定下一项改进，不自动建设更多能力。

验收：能追溯至少有用和无用案例；能说明哪项解释或记忆能力减少了用户负担。样本不足就记录未知，不能编造效果数据。

## 9. 测试聚焦不可破坏的行为

| 验证 | 预期 |
|---|---|
| 没有 question、没有历史 | 使用明确种子/主题发现；不报必填问题错误 |
| 指定一个作品链接 | 只补必要上下文，不触发无界全平台搜索 |
| 未知用途、一手证据充分 | 可进入意外发现；无需编造迁移用途 |
| 同行业但做法不同、跨行业但做法相同 | 不简单以行业标签决定价值 |
| 原文不支持推荐理由 | 不呈现为来源事实，重新生成或降级 |
| 单个平台失败或预算耗尽 | 返回部分结果及来源状态，不伪成功 |
| 候选不足50、重点不足3 | 显示实际结果，保留缺口 |
| 浏览与重复刷新 | 浏览不调用来源；刷新按预算和幂等规则执行 |
| 语义缓存上下文变化 | 偏好/问题变化后不复用不适用的理由 |
| 用户明确保存，无下一步 | 一次保存成功，不再要求确认或实验计划 |
| 重试同一保存请求、相似但不同反思 | 前者幂等；后者不能强制合并 |
| 模拟讨论被保存 | 可作灵感笔记，不能成为真人互动 |
| 同一新回复重复导入 | 一次事实、一次跟进事项 |
| 今天没时间 | 不据此永久排除人物或行业 |
| 旧文件与既有 JSON 调用 | 继续读取，不丢50人结果或历史关系 |

模型语义用固定样例人工复核；只为状态、预算、幂等、来源和接口等真实风险写自动化测试。遵守仓库现有 lint/typecheck/测试门禁，不为文案改动写镜像测试。

## 10. 成效、成本与扩展门槛

保留半年形成10–20位持续交流跨行业连接的方向目标；它不构成每次使用的强制任务。

分开呈现两类结果：

- 关系：最近30天真实且有具体内容的重复双向交流，沿用已有一致口径；模拟交流、批准和草稿不计入。
- 启发：用户主动保存了什么，之后是否使用或重新提到。保存仅证明用户当时想保留；只有用户实际表达认识变化时才称为“改变理解”。

不要求把所有灵感写成前后对比；不以保存数量最大化。不将试用、喜欢、共同实践和付款混成一个商业得分。

同时记录简明成本：每次阅读投入、刷新延迟、语义调用量。用于回答同样10–15分钟是否更容易找到值得继续的人或想法，而非只看输出量。

| 观察到的真实瓶颈 | 才考虑的扩展 |
|---|---|
| 可信发现反复集中在技术圈 | 调整来源种子、非技术查询和可读背景解释 |
| 简单组合反复错选，且有稳定人工样例 | 新增一项可解释排序特征 |
| 多次明确检索仍找不到已存笔记 | 改善文本检索；足够数据后再评估语义检索 |
| 用户多次主动开展共同实践且普通笔记不足 | 独立评审共同实践管理需求 |
| 用户明确需要周期获取 | 单独配置定时刷新；本次不自动创建任务 |

## 11. 边界与发布

Finch 维护人、作品、关系和启发的连续性。Quinn 负责按需深入研究与战略判断；builderDNA 负责痛点验证和构建机会；具体工具维护产品与收入事实。独立运行，按需手动传文本，不增加自动互调与共享模型。

现有作者立场确认、Critic、VoiceProfile 规则继续适用。用户保存灵感不自动转 AuthorIdea；用户选择形成观点时再调用原流程。用户明确确认过同一立场可复用现有有效确认，不能将“我觉得有趣”当作立场确认。

公开回复、私信、关注和发布仍由用户亲自执行。gh/opencli 只读。原有记录和可用模块不因定位变化被批量删除。

发布检查：三个入口均可用；最小闭环已真实演练；来源与预算可解释；无破坏性迁移；原 JSON/CLI 消费者有兼容或明确版本路径；README 与产品契约反映实际完成状态。

保留旧配置与推荐快照；新组合异常时可退回原浏览投影，继续访问历史笔记与关系。回滚不删除用户新保存内容。

## 12. 给实施 Agent 的执行说明

从P0开始，先核对代码后提交最小修改清单。首个目标是跑通“一个可信发现→一次用户选择→一条可回看的收获”，同时复用既有50人浏览与关系基础。P1验证后才固化稳定字段和规则；不得先创建完整探索引擎、多维评分体系或新技能集合。

每阶段报告实际修改、验证方式、结果与剩余限制。未执行的在线来源、未验证的关系效果和计划中的命令必须明确标注。
