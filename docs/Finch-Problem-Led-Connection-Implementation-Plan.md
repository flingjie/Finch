版本：v3，第一性原理 review 后的完整替代方案  
日期：2026-09-12  
状态：待实施；本次仅更新计划，没有修改项目代码。  
代码依据：此前静态阅读的 `flingjie/Finch@23ba4cfc036fcbe9e1e81ea55a004ab155f46756`，未在本次重新检查最新分支或运行测试。实施前比较差异，优先复用已存在能力。本文新增字段、命令、文件为拟议契约。

## 1. 目标与范围

Finch 在用户有限的注意力内，发现值得了解的人，找到真实的交流理由，并在需要时接上之前的对话。从实践和交流形成自己的观点与表达，继续服务于同行连接。

本轮首先解决：推荐视角相似、交流切入点不足、新面孔少。扩大可见选择，同时限制深度准备成本。

核心决策：

- 每日推荐单位是交流机会：一个人、一条具体内容、与用户的联系、可选下一步。
- 新发现默认展示 8–12 位去重作者对应的机会，质量不足少给；已有对话独立呈现，不占名额。
- 默认只深入准备用户选中的最多 3 位，可显式追加；实际互动不设数量任务。
- 当前问题、长期兴趣与开放探索共同驱动；不要求用户先创建问题。
- 同阶段实践者与互补经验者优先，同时覆盖资深者、实际使用者。
- 跨领域内容可以凭方法、约束或问题机制相关而进入。少量开放探索允许暂时用途不明，不能编造贡献理由。
- 显式反馈优先，浏览行为为弱信号；不以短期回复数独断推荐效果。

继续保留 Skill + Python 领域服务、统一 CLI、文件 Workspace、领域状态、幂等与发布门禁。Finch 与 builderDNA 独立，不恢复通用 Graph。个人经验与外部材料严格区分；费曼、sticky-message、表达练习、风格分析按需使用。目标分支如有 twitter-learning 则保留，基线目录未见该项，不为本次改造擅自删除或复制。

| 人的价值评分 | 对当前交流机会评分，人的历史作为上下文 | 价值依赖内容、用户处境和时机 |

## 4. 最小数据契约

### 4.1 兴趣上下文

扩展现有配置中的 interests；若现有结构不适合，使用单独的 discovery-context.yaml，并由 settings 加载，不同时维护两份真相。

字段：long_term_interests、current_questions（可空）、explore_directions、excluded_content。

问题保留自然语言文本即可，不增加 ID、状态机与跨对象关联。用户明确修改时更新，模型从行为推断的兴趣只作为建议。上下文变更生成指纹，供缓存失效使用。

只有用户反复跨会话围绕相同问题积累材料，且文本匹配已无法可靠关联时，才评估升级 FocusQuestion；不预建未来兼容框架。

### 4.2 交流机会

在 engagement 现有模型与仓储中定义轻量推荐条目 Opportunity，不新建领域系统，也不建立审批状态机。

| 字段 | 语义 |
|---|---|
| id | peer_id + 规范来源标识 + 内容版本派生的稳定 ID |
| peer_id | 关联已有同行身份 |
| source_refs | 原始帖子、评论、项目记录 URL/ID |
| source_excerpt / content_fingerprint | 可核对内容与去重依据 |
| discovered_via | 主题搜索、讨论延伸等来源路径 |
| topic_tags / role_tags | 可重叠的内容与角色标签，推断需标注 |
| why_relevant | 与兴趣、处境、问题或方法的具体联系 |
| opening | 提问、经验、不同观点或先了解的理由 |
| suggested_mode | learn / discuss / investigate |
| novelty_reason | 新证据、新方法、新约束等内容增量 |
| uncertainty | 未知背景、来源缺口或待核实之处 |
| assessed_at / assessment_version | 评估时间与缓存版本 |

“先了解”是合法结果，不要求每条开放探索都可立即互动。不从单条内容推断完整专业背景，不以粉丝量作为核心分数。

Opportunity 是发现结果，InteractionProposal 是用户选中后准备的具体提案；后者继续使用既有批准规则。批准仍不等于已经发布。

### 4.3 快照与呈现记录

缓存 Snapshot：id、created_at、context_fingerprint、source_coverage、failures、ranked_opportunity_ids、ranking_version。

持久的呈现记录：snapshot_id、opportunity_id、presented_at。仅实际呈现时记录，不把后台生成算作看过。界面/对话序号绑定 snapshot_id 与稳定机会 ID，换一批后不能选错人。

事实与推荐历史独立于可删除缓存。刷新失败保留旧结果，注明数据时间和覆盖缺口。

### 4.4 推荐反馈

复用决策仓储，增加 recommendation 类型，包含 opportunity_id、snapshot_id、dimension、value、reason、created_at。

- dimension=interest：worth_following / neutral / unsuitable。
- dimension=action：prepare / save_for_later / no_opening。
- reason 支持太熟悉、太泛、缺切入点、更多此类人及自由文本。
- 不强制每次填写两个维度；明确选择一个动作即可。
- 未展开不算拒绝，收藏不算准备交流，准备不算已发布。
- 不再推荐某人必须是用户明确决定；一次跳过只影响该机会。
- 用户明确撤销时覆盖派生偏好，保留决定历史；初期不在线训练权重，不写 VoiceProfile。

## 5. 发现、选择与成本控制

### 5.1 先用现有来源做宽

A 阶段使用已可用的主题搜索、现有 X/Reddit 或其他只读 adapter。搜索输入包括长期兴趣、可选当前问题、相邻机制表达与少量探索方向。

例如 Agent 失败恢复可扩展到补偿、故障复盘、检查点、人机交接。相关性通过具体机制解释，不要求出现 Agent 关键词。排除新闻搬运、融资与估值；有真实实践的发布帖不能仅因“发布”一词被删除。

当人工复盘发现现有来源持续同质化，再按缺口增加：

1. 优质讨论的一跳参与者：最多 3 条种子，每条最多 5 位新增作者，计入总预算。
2. 已有 GitHub 只读能力中的 Issue/PR 实际参与者。
3. 已发现技术博客链接的正文读取。

路径扩展仍在 peer-discovery 内，不新增独立 Skill。不做递归社交图谱，不把不同平台昵称相同当作身份合并证据。

### 5.2 分层预算

| 层级 | 默认初值 | 工作 |
|---|---|---|
| 轻量发现 | 目标 30–50 位作者，上限 50 | 多查询获取代表内容，去重粗筛 |
| 语义筛选 | 最多 20 位作者的代表机会 | 批量判断具体相关性、互补性、可交流性 |
| 每日展示 | 默认 10 位，目标 8–12 位 | 简短、可检查的机会卡 |
| 深度准备 | 每次默认最多 3 位 | 用户选中后补线程与更多历史，再生成提案 |

数量都是配置初值，合格候选不足不凑数。请求数、分页、墙钟时间均设置上限，部分失败返回可用结果；禁止对发现池每位作者启动重量级 Agent。普通浏览不生成完整回复。

### 5.3 选择一个有差异的组合

先质量准入：有真实来源、推荐理由具体、不违背排除项；讨论类机会需要合理切入点，学习类需要明确值得了解的内容。

随后由代码汇总结构化语义维度，并选择组合：

- 对当前机会看相关性、内容增量、互补性、可交流性；学习类不因暂时没有交流动作而被一律淘汰。
- 对整批结果看主题、方法、角色与作者重复，避免十条只是同一种观点。
- 初始尽量保留至少两条相邻/跨领域机会，以及最多一条开放探索；仅有合格候选才满足，不强制补齐。
- 同一作者每批一条主机会，其他相关来源可挂在该条；不占多个展示名额。
- 历史关系单列；不通过历史互动分数挤占新人。
- 同分按稳定 ID 排序，可重放；LLM 不输出最终总分或直接改状态。

分组只用于解释，可按当天标签自然分组；不恢复固定 4/3/2/1 配额。软目标不足时如实说明，不宣称达成多样性。

### 5.4 内容去重与新颖性

已呈现的相同机会默认不自动重现；more 排除当前会话已经呈现的内容。内容更新保留版本关系：格式修正不算实质新内容，新增结果、证据或明确问题才构成再次推荐理由。

作者新旧、内容增量分别记录。熟悉作者有新进展可以再次出现；仅重复作者且缺内容增量时软降权。证据不足以判断跨平台身份时标记潜在重复，不猜测合并。

## 6. 用户交互与 Skill 分工

用户说“看看今天有哪些人”时，peer-discovery 先检查快照；缺失或过期则在预算内刷新，失败可展示旧结果并说明。用户无需手动执行 refresh。

每日呈现：已有对话区列出需要处理的真实信号；新发现区展示 8–12 位轻量机会。可给一个主要行动建议，但不能因此只显示三个人。

每张卡默认：人是谁、具体内容链接、为何推荐、一个切入点或值得了解的理由。展开才补互补点、分歧、上下文；准备才生成完整草稿。默认 3 位深度预算是每次准备操作的上限，不限制浏览。

| 自然语言 | 行为 |
|---|---|
| 再给 5 位，别重复 | 使用快照剩余合格结果，无额外采集或推理 |
| 多一些不同领域的人 | 先从缓存按标签重选，不足时进行有界扩展 |
| 沿第 3 位讨论继续找 | 基于稳定来源，一跳扩展；能力不支持就明确说明 |
| 找有依据的不同观点 | 以具体分歧和来源筛选，不按情绪或冲突强度排序 |
| 今天只浏览 | 不自动进入回复准备与发布流程 |
| 这个值得了解，暂时不回 | 分开记录兴趣和行动意愿 |

缓存默认 24 小时过期，可调整。语义评估缓存键包含来源内容、用户上下文、提示词与模型版本；只重算受影响内容。more 用完合格缓存后告知可继续搜索，不静默全量刷新。

| Skill | 本次调整 |
|---|---|
| peer-discovery | 读取轻量上下文，必要刷新，解释机会，支持浏览/更多/范围扩展 |
| interaction-preparation | 选中后按需深读，默认具体提问，支持经验与小实验建议 |
| conversation-follow-up | C 阶段按真实触发信号恢复线程 |
| idea-discovery | D 阶段提炼用户判断，挑战一个假设，记录变化 |
| idea-to-draft | D 阶段保留用户原话，使用已确认立场 |
| voice-profile | 继续只从用户认可样本学习，不混入发现偏好 |
| weekly-reflection | 区分发现、选择、互动、回流中的失败原因 |

不新增 focus-question Skill；不为搜索路径、反馈、实验分别新增 Skill。

## 7. 拟议 CLI 与代码落点

用户通过自然语言操作；CLI 为 Skill 提供窄接口。以下命令应先对照目标分支，已有等效能力就扩展，避免重复。

| 命令 | 语义 |
|---|---|
| finch connect refresh | 有界刷新与快照持久化，返回覆盖情况 |
| finch connect today --limit 10 --json | 纯读取候选和关系投影，不调用网络/LLM |
| finch connect daily | 保留统一入口，默认同 today；显式 --refresh 可刷新 |
| finch connect more --snapshot ID --limit 5 | 剩余未呈现合格机会 |
| finch connect expand --from ID / --scope TEXT | 有界扩展来源或范围 |
| finch connect prepare --opportunity ID | 对指定机会深读准备，复用现有具体帖子能力 |
| finch connect feedback --file feedback.json | 校验并记录反馈 |

A/B 优先修改 engagement 的 models、search、peer_aggregation、relationship、既有查询构建器、settings、storage/repositories、cli 与 inbox/build_today_focus。先复用已有评分和缓存能力；只有责任无法容纳时才抽取小函数或文件。

更新 peer-discovery/SKILL.md、呈现参考和 skills/_shared/agent-presentation.md：明确轻量列表与深入卡片两种密度，解除旧“三条”规则对浏览列表的误用。同步产品契约、README、AGENTS、CLAUDE，解决旧 SQLite/Graph 叙述冲突。

## 8. 真实连接回流：C 阶段

A/B 不依赖本节全部完成；保留现有发布边界，先用已支持的事实记录路径。

复用 InteractionRecord，按需扩展 platform_message_id、author_identity、direction、reply_to_id、body、source_url、occurred_at、observed_at、verification_status、provenance。proposal_id 可空，支持系统外发生的交流。

- 平台消息 ID 优先幂等，URL 后备；重跑不刷新原发生时间。
- source_verified、user_attested、unverified 分开；手工录入不伪装平台验证。
- 记录过去事实不要求补做发布批准；未来发送仍走原门禁。
- 获取失败或缺正文标记未知，不推断回复存在。

线程优先用平台根消息关联；跨根/跨平台明确关联，不靠相似 topic 自动合并。保留旧 ID，给共识、分歧、未解问题补来源。承诺只从用户明确表达或认可结果生成，包含 owner、source_ref、status、可空 due_at、result_ref。

跟进信号：new_reply、own_commitment、new_evidence、related_update。时间仅辅助优先级和内部复查；无新增贡献不因超时联系对方。支持无需回应、推迟、关闭。触发信号及决定复用原决策记录，不建立任务引擎。

同步先探测现有平台能力；支持则增量读取，失败不推进游标；不支持则允许 URL/原文导入。新增 ingest/update/defer 等窄命令时复用已有领域服务。

## 9. 观点与表达：D 阶段

保持 AuthorIdea 的生产状态；用修订历史保存 claim、assumptions、counterexample、scope、source_refs、change_reason、confirmed_by_user、created_at，不把“已生成草稿”当作观点已证实。

保留 raw_user_text；默认使用已有原话，信息不足最多追问一个关键问题。草稿可表达有边界的假设，不把外部经验写成亲历。立场认可与发布决定分别处理。

小实验先嵌入线程/观点：假设、最小方法、期望观察、实际结果、产物引用。按需建议，不默认执行实验，不新建实验平台。失败和无结论正常记录。

周复盘提供少量具体消息与观点前后差异，结论引用来源，避免只有主题和数量。VoiceProfile 只从认可表达提出更新，不因点赞或发现反馈自动调整。

## 10. 文件存储与迁移

A/B：唯一临时文件＋同目录原子替换，所有持久化串行执行，IO 并行只收集结果、不并行改文件。幂等键、来源与原发生时间有测试。新字段可空/有默认值，旧记录能读取；不强制历史数据回填分类。

首版不启用后台写任务或多个写入入口同时执行。C 阶段若引入后台同步与前台写入重叠，必须先增加所有写入口共用的跨进程锁与版本检查；锁覆盖读改写，网络/LLM 在锁外。未实现保护不得开启并发写功能。

单文件原子性不等于多文件事务。以真实互动记录为权威，线程关联、今日投影可重建；中断后幂等补写修复。损坏文件报告且不静默覆盖。迁移提供 dry-run、备份、计数摘要，保留原始 ID 和审核状态。

## 11. 实施阶段与验收

### P0：确认基线与样本

核对目标分支、已有模型与来源能力；准备代表样本：熟悉观点、新人、老作者新实验、跨领域方法、仅值得了解的内容、缺来源、重复机会与平台失败。记录当前一轮结果和筛选时间作为对照。此步骤不重新做全面架构改造。

### A：推荐变宽

任务：轻量上下文、现有来源的查询扩展、交流机会条目、批量语义筛选、多标签组合选择、新旧关系分区、8–12 位简短展示。

验收：无 current_questions 也能运行；足量合格样本时返回目标数量的去重作者；真实跨领域方法不被关键词挡掉；同一作者新证据可进入；不足时少给；输出都有来源与具体推荐理由。无需先实现完整关系回流。

人工验收：用户能指出哪些新同行值得了解、哪些内容带来增量，以及不合适的原因。若仍然同质化，检查召回样本后再扩展来源，不盲目调评分。

### B：选择变轻松

任务：快照与呈现记录、more、按需展开/准备、兴趣与行动分离反馈、Skill 自动必要刷新、重复内容抑制、耗时和调用数记录。

验收：more 不重复、不额外调用网络或 LLM；编号映射稳定；普通列表不生成 10 份完整回复；每次默认深度准备最多 3 位，可显式追加；收藏不算发出；浏览时间与深度交流时间分别记录。

A/B 若已能提供有价值候选就进入 C；只有人工原因持续显示“来源太同质/缺实际参与者”，才追加讨论一跳、GitHub 或博客路径。各新增路径独立容错，不能阻断已有结果。

### C：连接能延续

任务：真实消息导入/只读同步、来源状态、线程上下文、明确承诺、事件跟进、推迟/关闭，以及需要时的跨进程保护。

工程验收：重复消息只一条且时间不漂移；新回复/承诺触发正确；过期本身不触发外部联系；平台失败不擦旧数据；关闭和推迟生效；跨文件中断可修复。

真实使用验收：完成至少一个实际互动记录案例；获得回复时准确恢复上下文。无回复案例正常记录，不算双向连接，不为验收自动追发。对外行动仍需用户授权。

### D：观点与实验深化

任务：用户原话、单次假设挑战、观点变化、可选实验、带来源的定性周复盘。

验收：能展示一条观点前后变化及依据，或者诚实说明尚未变化；有合适机会时完成一次“问题—不同观点—实验—结果—交流”案例。实验无结论不阻塞其他功能。

## 12. 必要验证与两周试用

复用既有单元/连接 E2E 测试，只补关键新增行为：内容指纹去重、老作者新内容、标签组合、空结果、缓存失效、more 无调用、反馈语义、事实/批准分离、幂等与阶段 C 的故障修复。语义质量用实际样本人工审阅，不用固定词命中测试替代。

两周试用从 A/B 可用时开始，不等待 D。第一周记录，第二周根据反复出现的明确原因只调整一个主要变量。小样本不宣称统计显著或因果结论。

| 观察 | 定义与用途 |
|---|---|
| 值得了解的发现 | 用户明确认可的机会与此前未接触作者，分别去重统计 |
| 内容增量 | 引发具体问题、想法、实验的机会；附用户理由 |
| 筛选负担 | 浏览选人时间与感知负担；不把主动深聊时间当坏成本 |
| 双向交流 | 真实消息支持的有内容来回；不是草稿数、外发数 |
| 持续关系 | 每周新增/加深、可继续的关系，系统举证、用户确认 |
| 系统成本 | 每层调用数、耗时、覆盖缺口、重复率与纠错次数 |

失败按步骤归因：没有召回好内容、推荐理由不成立、缺少可贡献内容、表达准备不适合、发出后尚无回应、上下文回流不准确。实际呈现数可作反馈分母，未反馈保留未知；未知行为不能视为拒绝。

验收方向：早期发现与内容增量改善，筛选负担不明显增加；最终观察实际交流与关系深化。若推荐变好但回复未增加，先检查切入点和观察窗口；若负担增加，先缩短卡片和改善浏览，不直接砍掉可浏览范围。

## 13. 延后项与触发条件

| 延后能力 | 何时再考虑 |
|---|---|
| 独立 FocusQuestion | 相同问题跨会话积累显著，轻量文本关联已不足 |
| 自动偏好学习/在线调权 | 显式反馈足够稳定且能解释错误推荐原因 |
| 多来源全面铺开 | 当前来源有明确、持续的覆盖缺口 |
| 社交图谱/向量检索 | 现有检索被真实规模限制，且收益可验证 |
| 独立实验对象 | 实验确需跨多个线程复用 |
| 并发写机制 | 后台同步与前台写入重叠前必须落实 |

自动公开发布、通用 Graph/任务引擎、跨项目集成、社交 CRM 均不进入本轮。
