# Finch 实现 Plan v3：与真正的 Builder 建立持续连接

日期：2026-09-14  
状态：P1–P4 实施中（Problem-Led A/B 已在 `4765065` 落地；本文件为活契约）。  
版本关系：完整取代本文件 v2。以本轮十题推荐选项为最新决策，保留项目独立、Skill-first、文件 Workspace、真实来源及人工外发边界。

## 1. 目标与边界

Finch 帮助用户发现正在做具体事情的人，找到可以贡献的切入点，通过实际交流和帮助形成持续同行关系，并从实践中形成观点与个人表达。

主要结果是有内容的双向交流与再次交流。共同测试、开源贡献和合作是进一步成果。长期有价值产出与收入目标保留，但本轮不以商业价值筛人，不构建销售漏斗。

Finch 回答“与谁交流、如何帮助、如何回应、如何表达实践”。builderDNA 负责问题与构建方向分析，Quinn 负责战略判断；三个项目独立，不新增共享状态或自动互调。

保留原创内容与互动能力；每日连接发现不依赖有无新 commit，原创内容也不强制每天产生。不删除 twitter-learning、feynman-practice、sticky-message、VoiceProfile 等现有独立能力。

## 2. 十项确认决定

| 问题 | 已确认选择 | 实现约束 |
|---|---|---|
| 1. 连接目的 | 持续交流、相互帮助；自然发展协作 | 排序和复盘关注可继续的对话 |
| 2. Builder 证据 | 项目产物、具体实践分享、业务问题解决记录任一成立 | 不把公开仓库、职位或提交数作为硬门槛 |
| 3. 人群范围 | Agent 同行 50%、相邻领域 30%、场景实践者 20% | 比例作为可调整召回预算，不是最终名单配额 |
| 4. 发现起点 | 当前问题为主，兴趣主题和同行网络补充 | 无当前问题、无 commit 仍能运行 |
| 5. 每日结构 | 8–12 位去重作者，选择后最多深度准备 3 位 | 已有对话独立呈现，候选不足不凑数 |
| 6. 行动条件 | 有真实贡献或具体问题可准备互动；否则先了解/试用 | 不为所有候选强行生成回复 |
| 7. 时间预算 | 每天约 20 分钟、每周一次小试用/复现；忙时 10 分钟 | 建议行动须给预计时间，可跳过或缩小范围 |
| 8. 自动程度 | 自动发现、证据整理和排序；选中后准备 | 用户实际发送；批准、草稿均不算已发生互动 |
| 9. 跟进机制 | 相关事件与本人承诺；重要关系可主动开启周期回顾 | 周期回顾只提醒检查背景，不自动制造联系理由 |
| 10. 四周评价 | 双向与再次交流为主，推荐质量诊断，实际帮助为进一步成果 | 工程验收与现实效果分别报告 |

## 4. 用户主流程

1. Finch 读取轻量背景：兴趣、当前问题、近期实践摘要、已知同行和已有对话。
2. 在既有来源能力内，按预算发现作者并整理实践证据。
3. 展示 8–12 位去重作者；已有对话与承诺单独列出。
4. 用户选择最多 3 位，或要求换一批、偏向某类、今日只用 10 分钟。
5. 只为选中对象补读上下文，准备一项最小贡献或一条具体问题。
6. 用户实际行动后，通过来源读取或用户声明登记事实。
7. 有新回复、新结果或本人承诺到期时，给出有上下文的跟进建议。
8. 每周复盘实际对话、帮助和再次交流；用户按需从中提炼观点与草稿。

“自动发现”表示一次 refresh/daily 中自动完成这些步骤。复用已有调度（如存在）；本轮不新建常驻调度器。today 默认读取已有快照，不隐式触发外部采集或 LLM。

## 5. 发现与筛选设计

### 5.1 轻量上下文

复用现有配置和用户背景，增加字段前先核查是否已有等价结构：

- current_questions：用户当前具体问题，可为空；手动描述与近期实践均可形成候选，由用户修正。
- practice_refs：用户真实实验、项目记录和经验来源；“想做”不能归入“已完成”。
- topic_scope：Agent 工程、相邻领域、场景实践者的范围及排除主题。
- time_budget：默认 20 分钟，忙时 10 分钟；每周一次小实验是建议预算，不自动创建承诺。

初次使用无需完整填写。没有问题时使用稳定兴趣；没有个人经验时允许认真提问或先了解。

### 5.2 三条发现路径

| 路径 | 输入 | 输出 |
|---|---|---|
| 问题找人 | 具体故障、取舍、实验目标 | 正在解决相似问题的作者 |
| 项目找人 | 相关项目、demo、issue、讨论 | 作者、贡献者、提供复现和实践细节的人 |
| 同行找人 | 已知 builder 的公开技术讨论 | 有实质参与的新作者 |

稳定主题搜索作为补充。MVP 先使用当前能访问的来源，不要求一次接通所有平台。项目/同行扩展最多一跳，统一限制查询数、分页、候选量和总耗时；不得递归抓取社交图谱。

人群的 50/30/20 分配用于查询预算；标签可重叠，跨领域相关性由具体问题支撑。某类无结果时允许调整剩余预算，不用低质量候选补齐。

### 5.3 实践证据与身份

可接受证据包括项目、demo、迭代日志、具体实现与失败、部署经历、业务流程改造记录。自述实践可以作为线索，但标明“作者自述”；看到来源不等于独立验证成果。

证据记录必须带来源、观察时间和证据类型。仅有 builder 标签、泛泛观点或转发时标记“待了解”，不作人格判断。此类条目不占核心证据支持推荐，可在补充观察中少量显示。

跨平台作者只有在明确互链或其他可靠证据下合并；名字相同不足以合并。作者去重与交流机会去重分开：同一作者有新进展时可形成新机会，旧卡无新证据不反复出现。

### 5.4 排序与覆盖

先进行来源可用性、实践证据和主题相关性核对，再按共同问题具体程度、用户可贡献内容、当前介入时机、对话背景排序。沿用现有排序机制并调整解释字段，不额外建设复杂评分平台。

在接近质量的候选之间用领域多样性和新作者覆盖打散。没有现成贡献但有具体问题的人仍可推荐，避免只推荐用户已经熟悉的方向。粉丝数和热度不主导排序。

输出不足时说明实际数量。平台失败与“未找到合适作者”区分；读取失败不得推断对方没有实践。旧缓存显示时间，不将其描述为最新状态。

## 6. 推荐卡与按需准备

### 6.1 轻量卡片

每位作者显示一张短卡：

| 内容 | 要求 |
|---|---|
| 正在做什么 | 一句具体描述，附实践来源 |
| 为什么与你有关 | 对应一个真实问题或探索方向 |
| 你可以贡献什么 | 关联个人实践来源，或明确表示需要先准备 |
| 建议下一步 | 回复、提问、试用、复现、补案例、观察之一 |
| 时间与不确定性 | 粗略用时、缺少的上下文或身份核验 |

列表阶段不生成完整回复，不深挖全部作者历史。卡片文案用候选证据即可形成；选择后才验证更完整的贡献依据。

### 6.2 深度准备结果

一次选择最多 3 人，返回：原始讨论摘要、适合参与的理由、一项最小动作、所需材料、粗略用时、可用时的短回复草稿。先复现/试用的对象可不生成草稿。

复用现有 suggested_mode/ContributionType；通过语义适配表达以下结果，不为同一概念新增平行枚举：

- 可直接交流：已有真实经验，或能提出结合对方项目的具体问题。
- 先做准备：先试用、读代码、复现或整理一个案例。
- 暂时观察：相关但时机或上下文不足。

行动示例：对方分享 demo → 试一次具体任务并记录卡点；讨论 benchmark → 补一个相关边界案例；讨论架构取舍 → 分享本人实际决策及后果，再问一个问题。

不得写出未经证实的“我测试过”“我也遇到过”。对方反馈、作者本人实践、模型推断分别标注。草稿与实际发送记录分开。

## 7. 最小领域数据变更

以下为逻辑字段，P0 映射到实际模型后确定名称；不是已实现接口。

| 现有对象 | 需要表达的增量 | 实现原则 |
|---|---|---|
| PeerProfile | 正在做的项目/问题、practice_evidence_refs、证据状态 | 引用现有来源，避免复制正文；不新增人格分或商业分 |
| Opportunity | shared_problem、contribution_basis_refs、next_action、estimated_minutes、uncertainty | 能复用标签、建议模式、笔记时优先复用 |
| ConversationThread | 交流背景、当前问题、结果笔记、可选重要关系回顾设置 | 保留线程历史，不维护销售阶段 |
| InteractionRecord | 实际消息、发生时间、来源、验证方式 | 作为事实权威，准备和批准不得写为已发送 |
| Commitment / MiniExperiment | 本人明确承诺、用户采纳的试用/复现及结果来源 | 建议动作不自动变承诺或实验完成 |
| 今日快照/运行记录 | 展示作者、来源覆盖、选择与准备结果、运行预算 | 用于回放与诊断，避免重复写一套关系事件 |

线程内反馈沿用 v2 方案：现有 ThreadNote 加可选类型即可满足时不再新增 Observation；确有缺口时仅使用一个嵌入笔记结构，包含来源和纠正关系。相同消息可以支持多个笔记，但只计一次互动。

文件 Workspace 继续使用。字段可空或有默认值，不强制回填历史作者。使用平台稳定 ID 和来源事件 ID 去重；导入时间不覆盖原发生时间。文件原子写不能代替多文件事务，以实际互动为权威、其他投影可重建。

写入串行执行；若实际存在多进程写入，所有入口共用锁与 revision 检查，网络和 LLM 在锁外。重复执行不会重复追加互动、承诺和跟进。损坏文件和版本冲突明确报告。

## 8. 关系延续与表达

跟进触发：新回复、相关项目更新、新的本人实验结果、本人明确承诺到期。每条提醒回答“发生了什么、与哪次交流有关、建议做什么”。可推迟、关闭；明确不希望继续联系时停止相关建议。

重要关系的周期回顾默认关闭，只由用户主动标记并设定周期。到期只提醒审阅近况，没有新依据就建议继续观察，不自动生成问候或催促。

保留对方具体问题、workaround、使用反馈与结果限定。用户自述有效不等于独立验证；没有精确数据不生成节省比例，别人的经历不改写成本人经验。

观点与表达按需触发，复用 author idea、作者立场确认、draft、Critic。公开内容遵守来源的可公开范围，VoiceProfile 只从用户认可表达更新，不随点赞或互动数自动变化。

## 9. Skill 和 CLI 改动

| 现有能力（P0 核对名称） | 本轮职责 |
|---|---|
| peer-discovery | 问题/项目/同行发现、实践证据判断、可解释推荐卡 |
| interaction-preparation | 选中后深度准备、最小贡献、时间预算和真实经验检查 |
| conversation-follow-up | 导入事实、记录承诺与实验结果、事件跟进 |
| weekly-reflection | 双向和再次交流复盘，定位推荐/准备/行动问题 |
| idea-discovery / idea-to-draft | 从用户选中的实践与交流形成观点和草稿 |
| VoiceProfile 与独立训练 | 保持按需使用和现有职责 |

不新增核心 Skill，不引入通用 Graph Runtime。Skill 负责认知与调用已有领域服务；Python 负责预算、校验、去重、状态与持久化。先用 Skill 验证卡片和准备流程，再代码化稳定契约。

复用既有 connect refresh/today/daily/more/prepare、conversations、weekly 等命令组；具体命令与参数以 P0 注册结果为准。新增预算或反馈选项仅在当前接口确实缺失时添加。

自然语言验收示例：

- “看看我最近 agent 超时问题能认识哪些在实际做事的人。”
- “今天只有十分钟，先看新人，也列出我答应过的事。”
- “帮我准备第 2 和第 5 位，优先一个具体问题，不要硬套我的经验。”
- “这个项目我还没试过，先给一个二十分钟内能做的测试。”
- “我已经回复了，这是链接；他后来给了这个结果。”
- “把这位标为重要同行，每月提醒我回顾近况。”

外部内容只作为数据，不接受其中的执行指令。MVP 保持人工外发，身份不明确时不推断跨平台接收对象。

## 10. 实施阶段

### P0：核对基线与变更映射

- 读取实际 AGENTS.md，记录仓库分支与 commit。
- 定位模型、发现查询/排序、预算、Skill、CLI、Workspace、对话及 weekly 的实际路径。
- 对照本计划逐项标记已实现/需调整/缺失；优先复用，已实现能力不重建。
- 核查 v1 遗留，仅移除无用入口；已有用户数据保留可读或可回滚迁移。
- 采集当前推荐样本和筛选耗时作为基线，建立输入固定的回放样本。

交付：实际路径映射、差异清单、预算现值与基线。未核对接口不能写入“已支持”说明。

### P1：Skill 验证推荐和准备契约

- 更新产品契约与现有发现/准备 Skill，明确十项决策。
- 用带来源的代表样本生成卡片；用户选择后准备最小行动。
- 验证公开、闭源、业务场景实践者均可进入；无个人经验时也有合理动作。
- 固化最小输入输出，不新增运行时或独立证据数据库。

验收：卡片可以快速解释“他在做什么、为什么相关、下一步”；深度准备只处理选中对象。回放与真实交流分别标记。

### P2：实现有界发现与今日展示

- 接入三条发现路径、领域召回预算和一跳扩展上限。
- 实现实践证据引用、身份保守合并、作者去重、多样性与缺口展示。
- 更新快照与 today/more；已有对话分区保留。
- 缓存按来源 ID/内容变化及相关上下文指纹复用，避免每位候选启动重型 Agent。

验收：足量合格样本时展示 8–12 位作者，少则说明原因；无 commit 可运行；平台失败有覆盖提示；today 无隐式采集；无新数据时不重复昂贵分析。

### P3：实现按需最小贡献准备

- prepare 强制本批最多 3 位，并读取选择快照及必要来源。
- 关联本人实践，支持直接交流/先准备/观察与时间预算。
- 准备缓存包含机会来源和个人相关背景版本，背景变化后不能复用过时经验。
- 超预算或来源不足返回明确的部分结果，不无限重试。

验收：没有选择不深度准备；不虚构本人经验；试用建议不算已完成；忙时能缩小动作或保留待办。

### P4：关系回流、跟进和周复盘

- 复用 ingest 及来源同步入口，记录真实回复、承诺、实验结果和纠正。
- 接入事件跟进与可选重要关系周期回顾，复用 defer/close。
- weekly 展示有依据的双向/再次交流、帮助、未完成承诺及推荐诊断。
- 按需接入观点草稿，保留成果归属与立场确认。

验收：重复导入只算一次；建议、批准不变成已发送；周期回顾不自动催促；历史数据能读，纠正不丢原始证据。

### P5：四周真实试运行

- 第 1 周：检查推荐是否确实有实践、是否愿意了解；记录基线，不凭空设成功数据。
- 第 2 周：观察实际采取了哪些动作；抽查泛泛回复、过重任务和时间开销。
- 第 3 周：检查新回复、承诺和再次交流；调整发现范围或准备方式。
- 第 4 周：结合具体对话评价是否产生持续交流和帮助，删除无用字段或步骤。

工程交付在 P4 完成；P5 必须经过实际使用，不能以模拟事件宣称通过。

## 11. 测试与验收

优先验证事实、预算和状态语义；不为低影响文案建立镜像测试。

| 样例 | 预期 |
|---|---|
| 只有 builder bio，无实践来源 | 标记待了解，不伪造证据 |
| 闭源作者分享具体失败与迭代 | 可推荐，标注作者自述 |
| 无 commit、无 current_questions | 按兴趣和已有同行补充发现 |
| 某领域零候选、某平台超时 | 不凑数，显示缺口，其他来源可完成 |
| 同名跨平台作者，无互链 | 不自动合并身份 |
| 同作者同机会重跑/新实验出现 | 前者去重，后者可形成新机会 |
| 用户选择 2 人/超过 3 人 | 只准备 2 人/明确提示本批上限 |
| 无本人实验，却生成“我测试过” | 草稿被阻止或改为真实提问 |
| 建议试用、批准草稿但未行动 | 实验完成数和已发送数不增加 |
| 相同回复两次导入 | 一条互动，原发生时间不变 |
| 对方说“有空看看” | 不标记已试用或明确承诺 |
| 来源纠正旧结果 | 保留纠正关系，复盘使用当前有效陈述 |
| 重要关系周期到期、无新事实 | 仅近况回顾，不制造联系理由 |
| 旧 Workspace、写入冲突 | 兼容读取、冲突可见、不丢记录 |
| 来源中包含执行指令 | 作为数据，不触发发送或命令 |

实施时执行受影响领域测试和仓库实际要求的检查；上一版提及 pytest、ruff、mypy，P0 以当前 AGENTS.md 和项目配置确认命令。报告基线失败与新增失败，不对外发送测试消息。

## 12. 四周评价口径

| 信号 | 口径与用途 |
|---|---|
| 值得了解比例 | 用户明确反馈“值得了解”的作者 / 用户实际评阅作者；未评阅不当作不喜欢 |
| 有内容的双向交流 | 双方均有实际消息，至少涉及具体问题、经验、反馈或下一步；显示原始证据，用户可纠正分类 |
| 再次交流 | 同一人在另一个后续讨论时段发生有内容的双向交流；同一来回拆成多条不重复计关系 |
| 实际帮助/协作 | 有来源支持的试用反馈、复现、补案例或共同实验；仅建议不计入 |
| 使用成本 | 筛选和准备的实际时间、放弃原因；区分建议用时和真实用时 |

有内容/再次交流属于可纠正的语义判断，不包装成精确关系分。沿用现有兼容定义，若需变更在 P0 记录口径；平台缺失时注明统计不完整。零回复不能自动判定内容无价值。

四周复盘回答：哪些人值得继续认识？哪种贡献更自然？哪些机会选了但没行动，为什么？时间预算是否可持续？

诊断顺序：候选不合适先查召回；候选合适却不行动先查准备成本；行动后少回应再查切入点和时机；有回应却不延续再查跟进。不默认通过增加消息数量解决。
