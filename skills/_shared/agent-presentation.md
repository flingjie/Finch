# 向用户呈现

Skill 调用 Finch CLI 之后，目标是帮用户做选择，不是汇报系统过程。

用户回复的结构固定为：

1. **结论**：范围与数量一句话（如「近 7 天 · N 条候选」）+ 点名最值得写的一条及理由。
2. **决策卡**：主视觉最多展开 3 条；其余折叠为一行列表。
3. **操作**：自然语言下一步（写 / 展开 / 比较 / 换一批）。

## 形状（真源）

```text
从近 7 天的 140 条候选中，最值得写的是：

**建立连接后，Agent 应该记住什么？** 〔最推荐〕

这次代码变更为互动记录增加了反思和后续动作。它背后真正值得讨论的不是字段设计，而是：同行发现只是开始，系统还要记住聊过什么、形成了什么判断，以及为什么值得再次联系。

这条最符合 Finch 的 connection-first 方向，也比单纯介绍功能更容易引发同行讨论。

另外两条可选：

2. 新发现的同行不应覆盖已有关系 — 能说明关系型 Agent 与普通推荐系统的区别
3. 代码迁移结束了，旧文档可能还困在旧架构里 — 清晰但相对常见

更接近实现细节、暂不优先：4. today-focus 的确定性排序；5. 为同行关系增加跟进时间；6. ……

回复「写 1」「展开 2」「比较 1 和 2」或「换一批」。
```

## 约束

- 开场只报范围与数量；不写 CLI / 翻库 /「挑末尾」等检索过程。
- 必须点名一条最推荐，理由落到产品方向或同行价值；可用 CLI 卡上的「可写观点 / 为什么值得写」，用自然中文改写（代码标识可保留）。
- 技术 `idea_*` 不写在标题里；agent 内部保留「序号 → idea_id」映射。
- 用户下一轮 → CLI：
  - `写 N` → `uv run finch ideas confirm {id}`，再 `uv run finch drafts create {id}`
  - `展开 N` → `uv run finch ideas show {id}`，再用人话补证据 / 冲突 / 角度
  - `比较 A 和 B` → 各一句差异 + 哪条更贴当前定位
  - `换一批` → 从本次未展示候选再挑最多 3 条；没有则说明并给 `uv run finch ideas list`
- 失败只说改变了结果的失败与重试；工具读写成功不必报。
