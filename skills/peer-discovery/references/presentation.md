# peer-discovery 呈现配方

见 `_shared/agent-presentation.md` 的共享原则。本文件是形状真源与命令映射。

## 三种密度

| 密度 | 何时 | 内容 |
|---|---|---|
| **首选机会** | 默认（「今天有什么值得交流的」） | 一条（0–1 条）：对象与话题 / 用户为何在意 / 对方为何可能接话 / 最小贡献 / 可见结果 / 成本与未知；**无完整回复草稿** |
| **轻量列表** | 浏览「今天有哪些人」（按请求） | 8–12 张：谁 / 内容链接 / 为何推荐 / 切入点或值得了解；**无完整回复草稿** |
| **深度卡片** | 用户选中后准备互动 | 最多 **3** 条：完整草稿 + 风险 + 批准命令 |

已有对话区独立呈现，不占发现名额。

## 形状（首选机会）

```text
今天我会优先跟进一个失败复现的讨论：@alice 已经保存 trace，但同一任务重跑结果仍不同，
现有回复主要建议增加运行次数。

这与你正在探索的「失败怎样变成回归测试」直接相关。我建议做一张「trace → 最小回放」
方法卡，先用一个含时间依赖的小例子展示哪些输入要固定、哪些结果允许变化；对方能拿自己的
trace 检查缺了什么，也可能补充边界。

先做这张卡吗？第一版只覆盖一个失败案例。
```

要点：

- 两三段自然语言，围绕「这次交流还缺什么，我们愿意补上什么」；不暴露内部 id / 状态 / 评分。
- 首选可为空：没有值得优先投入的讨论就明说原因（已解决 / 与现有回复重复 / 证据不足），
  并保留可浏览的线索，不硬凑、不编造对方困难。
- 用户接受 / 修改 / 拒绝都是自然语言；方向未选定前不自动做完整贡献包。

## 形状（浏览）

```text
今天有 10 个新交流机会（另有 2 条需要继续的对话）：

1. @alice — 新实验：failure replay + diff
   内容：https://x.com/alice/status/…
   为何推荐：与你的 checkpoint 实践具体重叠，有新增数据
   切入点：问他们如何验证补偿在部分失败后仍成立
   → 准备：uv run finch connect prepare --opportunity opp_…

2. @dave — 跨领域：saga 补偿表
   …
（先了解也可：模式 learn，不必立刻回复）

回复「准备互动 1」「展开 2」「再给 5 位」或「今天只浏览」。
```

## 用户下一轮 → CLI

- `准备互动 N` → `uv run finch connect prepare --opportunity {opportunity_id}`（每次默认最多 10）
- `展开 N` → 补互补点/分歧/上下文；仍不自动生成 10 份草稿
- `再给 5 位` / `换一批` → `uv run finch connect more --snapshot {snapshot_id} --limit 5`（不重复、不调网络/LLM）
- `今天只浏览` → 只 `connect daily`，不进入 prepare/approve
- 无快照或过期 → Skill 先 `uv run finch connect refresh`，再 `connect daily`
